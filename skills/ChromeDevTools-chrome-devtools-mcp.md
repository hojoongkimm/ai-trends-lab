## 1. 연구 배경 및 시스템 병목 (Systems Research Problem)

브라우저를 다루는 에이전트의 성능 한계는 "클릭할 수 있는가"가 아니라 **무엇을 얼마의 토큰으로 관측하는가**에서 발생한다. 도구 표면을 설계할 때 반복적으로 부딪히는 병목은 다음 세 가지다.

1. **관측 비용(Observation Cost)**: DOM 직렬화는 문서 크기에 비례하고, 스크린샷은 텍스트를 잃고 정밀한 지시 대상으로 쓸 수 없다. 두 방식 모두 페이지 복잡도에 대해 선형 이상으로 비용이 늘어나며, 컨텍스트 예산이 수만 토큰인 에이전트에게 페이지 하나가 예산을 다 쓸 수 있다.
2. **지시 대상의 안정성(Referential Stability)**: CSS 선택자는 리팩터링과 동적 렌더링에 취약하고, 좌표는 레이아웃 이동 후 거짓이 된다. 에이전트가 "관측한 대상"과 "행동한 대상"이 같은 객체임을 보장하는 참조 체계가 없으면, 도구 호출 성공률은 페이지 구조 변경에 그대로 노출된다.
3. **도메인 지식의 결손(Expertise Gap)**: 성능 디버깅의 산출물은 원시 트레이스가 아니라 통찰(insight)이다. 수 MB의 트레이스 이벤트를 컨텍스트에 넣는 것은 불가능하고, 넣는다 해도 "긴 작업이 몇 개였는가"를 모델이 스스로 집계해야 한다. 유용한 아티팩트는 "LCP가 3.2초이고 원인은 렌더 차단 리소스"라는 요약이다.

프로젝트는 이 문제를 설계 원칙으로 명문화한다. **토큰 최적화**(의미 요약 반환, 대용량 데이터는 파일로), **작고 결정론적인 블록**(마법 버튼 대신 클릭·스크린샷 같은 합성 가능한 도구), **값이 아닌 참조**(스크린샷·트레이스·비디오는 경로나 리소스 URI로), **자기 치유 오류**(맥락과 다음 행동을 포함한 오류), **점진적 복잡성**(기본은 고수준, 선택적 인자로 세부 제어). 이 원칙들은 서로 충돌하며, 아래 아키텍처는 그 충돌을 어디서 절충했는지를 보여준다.

## 2. 아키텍처 및 수학적 정식화 (Architecture & Formulation)

### A. 관측 표현: 접근성 트리 → 핸들이 붙은 텍스트 스냅샷

`take_snapshot`은 DOM이 아니라 접근성 트리를 직렬화한다. Puppeteer의 `accessibility.snapshot({ includeIframes: true, interestingOnly: !verbose })`를 호출하고, 10초 타임아웃을 걸며, 실패 시 "페이지가 내비게이션 중이거나 렌더러가 죽었을 수 있으니 이동·새로고침·다른 페이지 선택"을 안내하는 오류를 낸다. 관측 단위 $m$은 전체 DOM 노드 수 $n$보다 훨씬 작고, `interestingOnly`가 상호작용 가능한 노드로 프루닝하므로 비용은 $O(m)$이다. `InlineTextBox`처럼 부모 텍스트를 반복하고 백엔드 노드 id가 없어 도구가 지목할 수 없는 레이아웃 파편은 제거한다.

핵심은 식별자 부여 규칙이다. 새 노드에는 `uid = "{snapshotId}_{counter}"`를 주지만, **매핑의 키는 노드 자신의 정체성**인 `(loaderId, backendNodeId)` 쌍이다. 같은 노드가 다음 스냅샷에 다시 나타나면 이전 `uid`를 재사용하고, 보이지 않게 된 항목의 매핑은 제거한다.

$$
\mathrm{uid}_t(n) = M_t\bigl[(\mathrm{loaderId}_t(n),\; \mathrm{backendNodeId}(n))\bigr], \qquad M_t = \{\, \text{이번 스냅샷에서 관측된 쌍} \,\}
$$

이 규칙이 만드는 성질은 정확히 두 가지다. (i) **재렌더링에 강하다**: 같은 DOM 노드의 `uid`가 리페인트 후에도 유지된다. (ii) **내비게이션에 무효화된다**: `loaderId`가 바뀌면 같은 `backendNodeId`라도 새 정체성이다. 그래서 문서는 "항상 최신 스냅샷을 사용하라"고 요구한다. 프루닝이 오래된 `uid`를 풀어버리기 때문이다. 참조 수명(lifetime)이 내비게이션 경계와 정확히 일치하는, 흔치 않게 깔끔한 핸들 설계다.

### B. 도구 표면의 분할과 스키마 비용

문서화된 도구는 63개, 13개 범주다. 입력 자동화 10, 내비게이션 6, 에뮬레이션 2, 성능 3, 네트워크 2, 디버깅 10, 메모리 14, 네트워크 목 2, 확장 5, 서드파티 2, WebMCP 2, PWA 4, WebAuthn 1로 구성되고, 범주 플래그로 그룹 단위 제외가 가능하다. 기본값이 꺼진 범주가 많다는 점이 중요하다. 네트워크 목, 확장, WebMCP, PWA, WebAuthn, 서드파티 도구는 모두 옵트인이다.

도구 스키마는 요청마다 고정으로 지불되는 비용이다. 노출 도구 집합을 $T$, 스키마 토큰을 $s(t)$라 하면 요청당 고정 비용은 $\sum_{t \in T} s(t)$이고, `--slim`은 이 집합을 3개(내비게이션·스크립트 실행·스크린샷)로 줄인다.

$$
\frac{\lvert T_{\text{slim}} \rvert}{\lvert T_{\text{full}} \rvert} = \frac{3}{63} \approx 4.8\%
$$

즉 스키마 비용을 약 95% 절감하는 대신, 페이지 상태 진단 능력을 거의 전부 포기한다. 범주 플래그는 이 사이를 이산적으로만 조절할 수 있고, 턴마다 동적으로 도구 집합을 고르는 적응형 노출은 없다. 이 거친 양자화는 뒤에서 한계로 다시 다룬다.

### C. 성능 계측: 트레이스 → 통찰 파이프라인

`performance_start_trace` / `performance_stop_trace`로 기록한 트레이스는 다음 경로를 지난다.

| 단계 | 구현 | 설계 이유 |
| :--- | :--- | :--- |
| 수집 | CDP 트레이싱, 이벤트를 바이트 버퍼로 수신 | 중간 문자열 직렬화 회피 |
| 파싱 | `ChunkedTraceParser`가 버퍼에서 청크 단위로 이벤트 추출 | V8 문자열 할당 한계 회피 |
| 모델링 | 매 호출마다 새 `TraceEngine` 모델 생성 | 세션 격리와 메모리 잔존 방지 |
| 통찰 | `TraceEngine.Insights`가 내비게이션별 통찰 집합 산출 | 사람용 Performance 패널과 동일 엔진 |
| 보강 | Lighthouse 번들 감사, 선택적 CrUX 필드 데이터 | 실험실 데이터 + 실사용자 데이터 |

구조적으로 중요한 주장은 **패리티(parity)를 재구현이 아니라 임베딩으로 얻는다**는 것이다. `devtools-frontend`를 서브모듈로 두고 그 `TraceEngine`과 Insights를 그대로 호출하므로, 에이전트가 받는 분석은 DevTools Performance 패널이 계산하는 것과 같은 코드에서 나온다. 사람용 도구와 에이전트용 도구의 분석이 시간에 따라 갈라지는 드리프트가 구조적으로 차단된다.

메모리 측면의 이득은 피크 할당에 있다. 트레이스 전체 바이트 수를 $B$, 이벤트 수를 $E$, 청크 크기를 $C$라 하면, 단일 문자열 파싱은 문자열 하나에 $\Theta(B)$를 잡는 반면 청크 파싱은 피크를 $O(C)$로 눌리고, 파싱된 모델 자체는 어느 쪽이든 $\Theta(E)$다.

$$
M_{\text{naive}} = \Theta(B) + \Theta(E), \qquad M_{\text{chunked}} = O(C) + \Theta(E), \qquad C \ll B
$$

즉 절감은 모델이 아니라 **입력 문자열화 구간**에서 발생한다. 대용량 JSON을 다루는 다른 에이전트 도구에도 그대로 적용되는 지점이다.

### D. 메모리 포렌식: 객체 그래프 질의 표면

힙 스냅샷은 14개 도구를 가진 별도 서브시스템이다. `take_heapsnapshot`은 `.heapsnapshot` 파일 경로를 **필수**로 받는다(값이 아닌 참조 원칙의 직접 적용, `--memoryDebugging` 필요). 이후 요약, 클래스별 노드, 지배자(dominator), 리테이닝 경로, 중복 문자열, 객체 상세, 두 스냅샷 비교, "살아 있는 클로저가 읽을 수 없는 죽은 캡처 변수"를 보유한 컨텍스트 랭킹이 서버측 질의로 제공된다.

수십만에서 수백만 노드의 그래프를 다루므로 모든 응답은 페이지네이션과 상한을 갖고, 상한에 닿으면 **어느 한계에 도달했는지 명시**한다(`Note: results are truncated, the following limits were reached: …`). 잘림을 조용히 숨기지 않는 것이 이 표면의 신뢰성 근거다.

### E. 상태 보존 정책과 동시성

페이지별로 유지하는 관측 이력에는 명시적 상한이 있다. `--maxNavigationSaved`의 기본값은 3으로, 현재 내비게이션을 포함해 최근 3회분의 네트워크 요청과 콘솔 메시지를 본문까지 보존한다. 그 이전 내비게이션은 URL, 상태 코드, 요청·응답 헤더만 남겨 리다이렉트 추적에는 충분하지만 응답 본문은 일반적으로 사라진다. 메모리 상한을 $K=3$으로 고정한 슬라이딩 윈도우이며, 디버깅의 시간적 지역성(방금 무슨 일이 일어났는가)에 맞춘 선택이다.

동시성은 두 축으로 다뤄진다. (i) 하나의 서버를 여러 세션이 공유할 때 기본으로 `pageId` 라우팅을 켜서 각 세션이 자기 탭으로 호출을 보내게 하고, `--no-page-id-routing`으로 선택 페이지만 쓰는 고전 동작으로 되돌린다. (ii) 사용자 데이터 디렉터리는 기본적으로 재사용되며 한 번에 하나의 브라우저만 점유할 수 있으므로, 독립 세션에는 `--isolated`로 임시 프로필을 쓰게 한다. 자원 경합을 기능이 아니라 설정으로 노출한 형태다.

### F. 두 개의 소비자, 두 개의 전송

응답은 기계가 읽는 `structuredContent`와 사람이 읽는 텍스트를 함께 만든다. 오류는 다음 행동을 포함하도록 작성되고, 무거운 자산은 파일 경로로 반환된다. 같은 도구 레지스트리를 MCP 서버와 CLI 두 전송으로 노출한다는 점도 특징적이다. `chrome-devtools <tool> <pageId> …` 형태의 일회성 명령이 데몬에 붙어 같은 브라우저 세션을 조작하므로, 에이전트는 도구 호출 대신 **셸 스크립트를 생성**할 수 있다(CLI 스킬이 이를 가르친다). MCP의 구조화된 호출과 셸의 조합 가능성 사이의 절충을 전송 계층에서 해결한 사례다.

### G. 전송 경계의 정합성: 문자 단위 절단

가장 실무적인 세부는 문자열 절단이다. 제목 등 텍스트를 자를 때 `devtools-frontend`의 `truncateToCodeUnitLength`를 써서 **그래핌 경계**에서 멈춘다. 이유가 명시적이다. 서로게이트 쌍을 중간에서 자르면 단독 서로게이트가 남고, `JSON.stringify`는 이를 `\ud83d` 같은 이스케이프로 직렬화하며, 엄격한 JSON 파서(예: Python MCP SDK)는 이를 거부한다.

$$
\text{cut}(s, L) = s[0 : \max\{\, i \le L : s[i] \text{는 그래핌 경계} \,\}]
$$

전송이 JSON인 한, 이미터는 유효한 UTF-16 스칼라 시퀀스만 내보내야 한다. 이런 결함은 에이전트의 추론 실패처럼 보이지만 실제로는 인코딩 계약 위반이며, 프롬프트 개선으로는 고칠 수 없다.

## 3. 구조적 비교 (Comparative Positioning)

같은 목표(브라우저를 에이전트가 다루게 하기)를 이루는 네 가지 경로와 비교한다.

| 항목 | 원시 CDP 스크립팅 | Puppeteer/Playwright API 직접 사용 | 스크린샷 전용 컴퓨터 유즈 | Chrome DevTools MCP |
| :--- | :--- | :--- | :--- | :--- |
| 초기 설정 비용 | 높음(프로토콜 직접 구현) | 중간(코드 작성 필요) | 낮음 | 낮음(`npx` 한 줄) |
| 관측 비용 | 사용자 정의 | 사용자 정의 | 이미지 토큰, 텍스트 손실 | 접근성 트리 $O(m)$ + 핸들 |
| 지시 대상 안정성 | 직접 관리 | 셀렉터 의존 | 좌표 의존 | 정체성 기반 `uid` |
| 성능 통찰 깊이 | 원시 이벤트 | 없음(직접 분석) | 없음 | TraceEngine + Lighthouse + CrUX |
| 컨텍스트 보호 | 없음 | 없음 | 없음 | 요약·파일 참조·페이지네이션 |
| 이기종 클라이언트 | 없음 | 없음 | 없음 | MCP + CLI + 8종 스킬 |

수치로 확인되는 규모는 도구 63개·범주 13개, `--slim` 3개, 릴리스 65회, 접근성 스냅샷 타임아웃 10초, 내비게이션 보존 창 3회, 소스 약 31k LOC(TypeScript)다. 이 조합에서 이 프로젝트의 고유점은 **분석 엔진의 사람 도구 패리티**와 **관측 표현의 정체성 설계**에 있고, 반면 도구 수가 많아 스키마 고정 비용이 크다는 점은 다른 경로 대비 불리한 축이다.

## 4. 한계점 및 실패 모드 (Limitations & Trade-offs)

1. **관측의 본질적 손실성**: 접근성 트리는 DOM이 아니다. 캔버스·웹GL 콘텐츠, 시각적 회귀(간격·색·겹침), 접근성 트리에 기여하지 않는 장식 요소는 보이지 않는다. `interestingOnly` 프루닝은 필요한 노드를 숨길 수 있고, 그 경우 `verbose`로 되돌려야 하는데 에이전트는 숨겨진 것을 모르므로 스스로 판단하기 어렵다.
2. **참조 무효화의 조용한 실패**: `uid`는 내비게이션에서 죽는다. 긴 에이전트 루프는 이전 스냅샷의 핸들을 재사용하는 경향이 있고, 그 오류는 "요소를 찾을 수 없음"으로 나타나 원인 진단을 어렵게 만든다. 핸들 수명이 문서화되어 있지만 프로토콜 수준에서 강제되지는 않는다.
3. **계측의 대표성**: 개발 기계에서 1회 기록한 트레이스는 실사용자 분포가 아니다. CrUX 필드 데이터가 이를 보완하지만, CrUX는 트래픽 임계치를 넘는 공개 오리진만 포함하므로 로컬·스테이징에는 필드 신호가 없다. 성능 도구가 주는 확신은 환경 의존적이다.
4. **데이터 경계의 기본값**: 사용 통계 수집이 **기본 켜짐**이고(옵트아웃 플래그와 `CI` 환경 변수로 해제), 성능 도구는 트레이스 URL을 CrUX API로 보낼 수 있다(`--no-performance-crux`로 해제). 네트워크 헤더 마스킹도 기본은 꺼짐이다. 문서화되어 있으나, 기본값이 수집 쪽에 서 있다는 사실은 조직 환경에서 그대로 수용되기 어렵다.
5. **브라우저 스코프**: 공식 지원은 Google Chrome과 Chrome for Testing뿐이다. 다른 Chromium 계열은 동작할 수 있으나 보장되지 않으며, 확장 안정 채널 최신 버전에 대한 지원을 약속하는 구조다.
6. **보안 경계는 브라우저 전체**: 서버는 브라우저 인스턴스의 내용을 MCP 클라이언트에 그대로 노출한다. `--javascriptEvaluation=false`는 평가 진입점만 막고, 문서 스스로 "이것은 자바스크립트 샌드박스가 아니다"라고 밝힌다. 클릭·입력으로 유발되는 페이지 스크립트는 계속 실행되고, `--fileNavigations=false`도 파일시스템 샌드박스가 아니다. 격리는 OS 수준에서 해야 한다.
7. **스키마 비용의 거친 제어**: 63개 도구의 스키마는 요청마다 지불된다. 범주 플래그는 그룹 단위 이산 절단이고, `--slim`은 3개까지 떨어뜨린다. 중간 해상도(예: 성능+디버깅만)는 범주 조합으로만 가능하고, 작업 난이도에 따른 동적 노출은 없다.
8. **공개 벤치마크 부재**: 저장소 안에 에이전트 브라우저 과업의 성공률 벤치마크가 없다. 가치는 설계 원칙과 엔지니어링 세부로 주장되지만, "이 도구 표면이 다른 표면보다 나은가"는 이 저장소의 증거로 답할 수 없다.

## 5. 연구 및 실무 활용 포인트 (Research Impact)

- **관측 설계가 컴퓨터 유즈 에이전트의 1차 지렛대**: 접근성 트리 + 정체성 기반 핸들 + 토큰 예산이라는 조합은 재사용 가능한 패턴이다. 게임 에이전트의 씬 그래프 객체 id, 로보틱스의 객체 트랙 id와 같은 계열의 해법이며, "관측 표현이 행동 성공률을 결정한다"는 명제를 실증할 수 있는 비교 대상이 된다.
- **인간 도구의 임베딩으로 패리티 확보**: 분석 엔진을 재구현하지 않고 `devtools-frontend`를 그대로 쓰는 선택은, 에이전트 도구 일반의 원칙으로 확장된다. 도구가 사람용 제품과 같은 엔진을 쓰면 분석 드리프트가 사라지고, 대신 사람용 엔진의 제약(번들 크기, 서브모듈 빌드)을 떠안는다. 이 교환은 흔히 잘못 계산되며, 여기서는 명시적으로 계산되어 있다.
- **대용량 객체 그래프의 질의 표면 설계**: 힙 스냅샷 14개 도구는 "파일로 받고, 요약·페이지·상한 명시로 질의한다"는 패턴의 완성된 예다. AST, 트레이스, 프로파일러 덤프, 데이터프레임에도 같은 형태가 적용된다. 잘림을 `limitsReached`로 표면화하는 규약은 재현성 측면에서 특히 중요하다.
- **전송 계층 정합성**: 그래핌 단위 절단, 단독 서로게이트 회피, 엄격 JSON 호환은 에이전트 실패처럼 보이는 상호운용 결함의 전형이다. 도구를 만드는 쪽에서 검사해야 할 항목 목록으로 그대로 쓸 수 있다.
- **후속 연구 방향**: (i) 도구 스키마 고정 비용 대비 과업 성공률의 곡선(63개·3개·중간 해상도의 비교), (ii) 스냅샷 프루닝 정책과 핸들 수명이 성공률에 미치는 영향, (iii) 통찰 집합의 충실성(진짜 병목을 통찰이 덮는가) 검증, (iv) 재현 가능한 페이지 픽스처를 갖춘 브라우저 에이전트 하네스 벤치마크, (v) 실험실 트레이스와 필드 데이터의 괴리를 에이전트가 어떻게 화해시켜야 하는가.
