## 1. 연구 배경 및 문제 정의 (Research Problem)

코딩 에이전트의 웹 개발 성능 저하는 모델 크기가 아니라 **학습 데이터의 시간 분포**에서 발생한다. 사전학습 코퍼스에는 과거 10여 년의 코드가 압도적으로 많으므로, 에이전트는 이미 플랫폼이 기본 제공하는 기능에도 습관적으로 라이브러리·폴리필·명령형 자바스크립트를 생성한다. 두 번째 결함은 지식의 **밀도**다. 모델이 어떤 API의 존재를 알아도, 프로덕션 수준의 구현 패턴(폴백, 접근성 상태 동기화, 경계 조건)을 충분히 담고 있지 않으면 결과물은 "동작하지만 낡은" 코드가 된다.

이 문제를 "가이드 문서를 스킬로 붙인다"는 발상으로 풀면 즉시 두 번째 벽에 부딪힌다: **컨텍스트 예산**. 코퍼스는 수백 개 기능과 200여 개 사용 사례로 이루어져 있고, 이를 통째로 시스템 프롬프트에 넣는 것은 불가능하다. 따라서 이 프로젝트의 실제 대상은 문서가 아니라 **검색·주입 시스템**이며, 문서는 그 시스템이 소비하는 데이터다. 즉 (i) 무엇을 가르칠지(코퍼스 설계), (ii) 무엇을 생략할지(프루닝), (iii) 필요할 때 얼마의 토큰으로 꺼낼지(검색)의 세 문제를 동시에 푼다. 이 저장소는 그 세 문제를 각각 **평가 하네스로 측정 가능한 대상**으로 만든다는 점에서, 일반적인 "프롬프트 모음" 스킬과 구분된다.

## 2. 아키텍처 및 수학적 정식화 (Architecture & Formulation)

### A. 코퍼스 구조: 가이드 = 문서 + 데모 + 기대사항 + 평가 자산

가이드는 `guides/<category>/<use-case>/` 단위로 존재하며, 디렉터리 하나가 **하나의 평가 가능한 단위**다.

| 파일 | 역할 |
| :--- | :--- |
| `guide.md` | 에이전트에 주입되는 본문(패턴, 폴백, 함정, Baseline 조건) |
| `demo.html` | 실행 가능한 참조 구현 |
| `expectations.md` | 채점 가능한 구현 요구사항(자연어 → 체크리스트) |
| `targets/<app>/task.md` | 실제 베이스 앱에 대한 개발자 요청 프롬프트(API 이름을 언급하지 않음) |
| `targets/<app>/grader.ts` | Playwright 기반 채점기(소스 패턴·계산된 스타일·런타임 DOM·접근성 상태) |
| `targets/<app>/patches/*.patch` | 골든 솔루션(에이전트별) 및 zero-passrate 기준선 |

저장소에는 `guides/` 아래 2,362개 파일이 있고, 범주는 UI 동작(420), UI 컴포넌트(281), 성능(259), 시각 디자인(224), 보안(224), CSS(196), 폼(194), UI 아톰(122), HTML(117), PWA(53), WebMCP(50), 빌트인 AI(46), 접근성(46), 사용자 경험(41), JS(41), WASM(21), 프라이버시(21)의 17개다. 커버리지 표는 **250개 현대 웹 기능**(CSS·레이아웃 140 / HTML·DOM 36 / JS·API 74)과 **203개 실제 개발자 사용 사례**로 집계된다. 즉 이 코퍼스는 "기능 목록"이 아니라 "요청 → 구현" 매핑의 사전이다.

### B. 하이브리드 검색: 비대칭 임베딩 + BM25 + RRF

에이전트는 스킬 활성화 후 `modern-web-guidance search "<query>"`를 호출하고, 반환된 ID로 `retrieve`를 실행해 본문을 컨텍스트에 삽입한다. 검색은 네트워크·API 키 없이 로컬에서 수행되며, 두 개의 순위를 융합한다.

**(1) 어휘 순위(Okapi BM25).** Lucene `EnglishMinimalStemmer`로 토큰화하고, 청크에 가이드 제목·범주·`web-feature` ID(원형 + 언슬러그 형태)를 헤더로 선부착해 정확한 식별자에 대한 어휘 재현율을 확보한다.

$$
\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d)(k_1 + 1)}{f(t,d) + k_1\left(1 - b + b\dfrac{|d|}{\text{avgdl}}\right)}
$$

**(2) 밀집 순위(비대칭 정적 임베딩).** 문서 청크는 빌드 시 교사 모델(`gemini-embedding-001`, 768차원 → MRL 256차원, L2 정규화)로 임베딩해 Int8로 양자화해 커밋한다. 질의는 런타임에 **정적 단어 테이블**로 약 30µs에 임베딩된다. 이 비대칭 설계의 근거가 저장소에 정량적으로 제시되어 있다: 3개 단어 질의를 합성하면 256차원에서 평균 쌍별 코사인이 0.28로 날카롭지만, 약 300단어 청크를 평균하면 모든 문서가 공유 영어 빈도 중심으로 끌려가 코사인 0.970의 좁은 원뿔(cone)로 붕괴한다. 대칭 실험에서는 "best pizza in new york" 같은 무관 질의가 `<dialog>` 문서와 0.899의 코사인을 기록했다. 질의는 소수 단어의 합, 문서는 전용 교사 벡터로 두어 이 붕괴를 우회한다.

**(3) 순위 융합(RRF)과 게이트.**

$$
\text{RRF}(d) = \sum_{r \in \lbrace \text{dense}, \text{bm25} \rbrace} \frac{1}{k + \text{rank}_r(d)}, \qquad k = 60
$$

게이트는 BM25가 0건일 때만 밀집 코사인 하한 0.30을 강제하고, BM25가 키워드를 잡으면 하한 미만의 밀집 후보를 구조(rescue)로 유지한다. 둘 다 없으면 빈 배열을 반환해 범위 밖 질의를 명시적으로 거절한다. 이 "어휘 우선 게이트"는 오탐 유입과 무응답 폴백(카탈로그 전체를 덤프하는 1,500토큰 낭비) 사이의 균형점이다.

**(4) 토큰 경제.** 출력은 $K = 10$개의 압축 항목(`{id, description}`, 항목당 약 53토큰)으로, 기존 $K=5$의 상세 항목(약 105토큰)과 같은 약 530토큰 예산에서 후보 커버리지를 2배로 늘리며 Hit@K를 7.4%p 개선했다. 부수적으로 9.5KB를 넘는 `retrieve` 출력은 에이전트 하네스의 중간 절단을 피하기 위해 `/tmp` 파일로 자동 분기된다(가이드의 76.6%는 9.5KB 미만이라 인라인 유지).

양자화 오차는 행별 스케일 $s_i = \max_j |E_{ij}| / 127$로 상한이 정해진다.

$$
\left| \hat{E}_{ij} - E_{ij} \right| \le \frac{s_i}{2}, \qquad \text{cosine fidelity} > 0.999
$$

### C. 검색 품질의 목적함수: SNR

일반적인 IR 지표(recall, nDCG)는 에이전트의 소비 방식을 반영하지 못한다. 이 프로젝트는 **관련성과 토큰 낭비를 하나의 스칼라로** 결합한 Signal-to-Noise를 정의한다.

$$
\text{SNR} = 0.7 \cdot \text{Recall} + 0.3 \cdot \text{LeafNDCG} - \text{TokenTax}
$$

무관 가이드 100토큰당 1.4점이 차감되고, 500토큰을 초과하면 100토큰당 4.5점으로 가팔라진다(볼록 페널티). 답변 가능한 질의가 빈 배열을 받으면 카탈로그 덤프 폴백 비용 1,500토큰이 부과된다. 이 설계는 "검색이 조금 더 맞히는 것"과 "컨텍스트를 적게 쓰는 것"을 동일 단위에서 교환 가능하게 만든다. 평가셋 자체도 오염 방지 규칙을 갖는다: 실사용 질의 4,000건을 **어간 토큰 집합이 겹치지 않도록** 2,000/2,000으로 분할하고(wild-v2), 에이전트 질의 1,029건은 정답 가이드의 연결 성분으로 dev/test를 갈라(515/514) 가이드 누출을 막으며, LLM 판정자는 인간 평가 69건과 0.78의 이차가중 Cohen's $\kappa$로 캘리브레이션되었다.

### D. 프루닝: "기회(opportunity)"와 "상승분(uplift)"의 분리

프루닝의 기준은 문서 품질 판단이 아니라 **평가 결과의 잔여 신호**다. 각 태스크에 대해 무가이드 통과율 $p_0$, 가이드 통과율 $p_1$이 있을 때,

$$
\text{opportunity} = 1 - p_0, \qquad \text{uplift} = p_1 - p_0
$$

기회가 0에 가까운(모델이 이미 잘하는) 영역의 조언은 중복이므로 제거하고, 상승분이 큰 영역의 가이드를 정교화한다. 요소 $g$의 상승분과 토큰 비용 $\tau(g)$에 대해 유지 규칙을 쓰면 다음과 같다.

$$
\text{keep}(g) \iff \frac{u(g)}{\tau(g)} \ge \lambda
$$

여기서 $\lambda$는 컨텍스트 1토큰의 기회비용이다. 이 정식화는 저장소가 명시한 기준("이미 성공하는 조언은 프루닝")의 직접적 귀결이며, 스킬 팩 토큰 예산(본체 약 205토큰, 확장 팩 약 175토큰)이 극단적으로 작은 이유를 설명한다.

### E. 채점기 캘리브레이션: 100% / 0% 이중 기준

평가 파이프라인(`gd dev`)은 5단계다: (1) 골든·zero-passrate 패치 생성, (2) `expectations.md`로부터 Playwright 채점기 생성, (3) **캘리브레이션** — 골든은 100% 통과, 미수정 베이스 앱은 100% 실패, (4) 가이드 유무 에이전트 실행, (5) 실패 체크 분석 리포트. 3단계가 핵심이다. 채점기가 골든을 통과시키지 못하면 측정 자체가 무효이고, 베이스 앱을 통과시키면 개선 여지가 0인 태스크가 되어 상승분이 사라진다. 이 두 극단을 동시에 만족해야만 태스크가 유효 판정을 받는다. 태스크 프롬프트가 API 이름을 언급하지 않는다는 점도 중요하다 — 에이전트가 **스스로 발견·검색**하는 능력을 측정하기 위한 조건이다.

### F. `legacy-scan`: 부채 청산 경로

주입(주도적 안내)과 대칭적으로, 이미 존재하는 코드베이스의 레거시 관용구를 찾는 정적 분석기가 함께 배포된다. 구조는 2계층이다.

1. **정적 매처(Static Matcher)**: AST 기반 스캐너(CSS, DOM, JS, 의존성, SFC 추출)와 규칙별 탐지기로 후보를 찾고, 컨텍스트 슬라이서가 해당 라인의 전후 문맥을 잘라낸다. 규칙이 없는 가이드는 정적 탐지 대상에서 제외되므로, 한 실행에서 검사되는 범위는 코퍼스의 일부다(문서 예시 실행에서 37개 가이드·41개 규칙, 약 20%).
2. **LLM 검증기(LLM Verifier)**: 각 규칙은 `keepWhen` / `dropWhen` 루브릭을 가지며, 후보는 이 기준으로 유지·폐기된다. 출력은 사람용 텍스트와 에이전트용 JSON(파일 좌표, 메시지, 루브릭, `retrieve` 명령) 두 형태다. 정적 결과가 **잠정적(provisional)** 이며 루브릭으로 검증해야 한다는 경고를 출력에 명시하는 것은, 정적 매칭의 오탐률을 숨기지 않겠다는 설계 입장이다.

## 4. 한계점 및 실패 모드 (Limitations & Trade-offs)

1. **합성 평가 환경의 외적 타당성**: 태스크는 두 개의 베이스 앱(`daily-grind`, `devtools-times`)에 대해 정의된다. 실제 프로덕션 저장소의 프레임워크·빌드 체인·레거시 제약과는 거리가 있으며, 앱 수가 적다는 것은 태스크 간 상관(같은 DOM 구조·같은 스타일 시스템)이 상승분 추정의 유효 표본을 줄인다는 뜻이다.
2. **채점기의 표면성**: Playwright 검사는 소스 패턴, 계산된 스타일, 런타임 DOM, 접근성 상태를 본다. 따라서 요구사항을 형식적으로 만족시키면서 의도된 설계를 어기는 구현(예: 기대 속성만 추가하고 실제 동작은 유지)을 통과시킬 수 있다. 100%/0% 캘리브레이션은 극단 오류를 잡지만, 중간 구간의 판별력은 별도 검증이 필요하다.
3. **상승분의 포화와 선택 편향**: 이미 잘하는 영역을 프루닝하는 전략은 평균 상승분을 높이지만, 프루닝 후 남은 태스크 집합은 "모델이 약한 영역"으로 편향된다. 이 값은 코퍼스 전체의 유용성 지표로 읽을 수 없고, 시간이 지나면 모델 개선에 따라 태스크 자체가 무효화된다(재캘리브레이션 부채).
4. **정적 임베딩의 표현력 상한**: 단어 룩업 테이블 기반 질의 임베딩은 어휘에 없는 신조 식별자(CSS 속성·API 이름)를 표현하지 못한다. 새 식별자가 등장하면 어휘 재훈련이 필요하고, 그 전까지는 BM25 경로에 의존한다. 이는 결정론적·저비용 검색의 대가다.
5. **텔레메트리 기반 평가셋의 분포 이동**: 질의 데이터가 CLI 텔레메트리(에이전트가 생성한 검색어)에서 유래하므로, 실제 사용자 의도 분포와 어긋날 수 있다. 또한 무응답 폴백 비용 1,500토큰, 무관 가이드 페널티 계수(1.4/4.5) 같은 SNR 가중치는 공학적 판단값이며 최적화 근거가 공개되어 있지 않다.
6. **`legacy-scan`의 부분 커버리지**: 정적 규칙이 있는 가이드만 검사하므로(예시 실행 37/약 200 가이드) "발견 0건"은 "레거시 없음"을 의미하지 않는다. 출력이 이 한계를 명시하지만, 사용자는 부분 스캔을 전체 스캔으로 오독하기 쉽다. 또한 정적 매칭은 문맥 의존 결함(의도적으로 유지된 구형 패턴, 폴백 목적의 코드)에서 오탐을 만들며, 이를 걸러내는 LLM 검증기는 추가 비용과 자체 분산을 도입한다.
7. **기능 게이팅의 운영 복잡도**: Origin Trial·변동성 기능은 `search`로는 보이지만 `retrieve`가 차단되어, `.mwgrc` 옵트인 없이는 접근할 수 없다. 안전성 측면에서는 옳지만, 에이전트가 "검색은 되는데 열리지 않는" 상태를 만나 우회 시도(카탈로그 덤프)로 흐를 수 있는 UX 실패 모드가 존재한다.
8. **유지보수 규모**: 가이드 1개당 문서·데모·기대사항·2개 앱의 태스크·채점기·에이전트별 패치가 필요하다(2,362개 파일). 콘텐츠 추가의 한계비용이 높고, `expectations.md`가 갱신되면 채점기·패치 재생성이 필요하다(저장소는 이를 stale eval로 표시하고 파이프라인 이슈로 추적한다).

## 5. 연구 및 실무 활용 포인트 (Research Impact)

- **스킬을 "문서"가 아니라 "검색 시스템"으로 설계하기**: 컨텍스트 예산이 고정된 이상, 스킬의 성능 상한은 검색 품질이 결정한다. 이 저장소는 스킬 본체를 약 205토큰으로 유지하고 본문은 필요 시 주입하는 구조를 택했다. 스킬·에이전트 도구를 설계할 때 재사용 가능한 원칙은 (i) 인덱스는 오프라인·결정론적으로, (ii) 질의는 저지연으로, (iii) 반환은 압축 ID + 짧은 설명으로, (iv) 범위 밖 질의는 명시적으로 거절하는 것이다.
- **SNR류 목적함수의 일반화**: `0.7·Recall + 0.3·nDCG − TokenTax`는 검색 품질과 컨텍스트 비용을 하나의 스칼라로 만든 실용적 예다. RAG 기반 에이전트 평가에서 "정답 포함률"만 측정하면 토큰 낭비가 보이지 않으므로, 볼록 페널티를 포함한 SNR 형태의 목적함수는 다른 도메인(문서 검색, 코드 검색, API 레퍼런스 검색)으로 이식 가능하다.
- **평가 기반 콘텐츠 프루닝**: 기회(opportunity)와 상승분(uplift)을 분리해 $u(g)/\tau(g) \ge \lambda$로 유지 여부를 결정하는 규칙은 지식 편집(knowledge editing)과 프롬프트 압축 연구의 실무적 교차점이다. "모델이 이미 아는 것을 가르치지 않는다"는 원칙을 측정 가능한 절차로 만든 사례다.
- **비대칭 검색의 이론적 근거**: 정적 임베딩에서 문서 평균화가 코사인 원뿔 붕괴를 일으킨다는 관측(0.28 vs 0.970, 무관 질의 0.899)은 소형·오프라인 RAG 시스템 설계에서 일반화 가능한 경고다. 질의측과 문서측의 표현을 분리하면 저비용을 유지하면서 붕괴를 피할 수 있다.
- **후속 연구 방향**: (i) 스킬 요소 단위의 자동 프루닝(문단·예제 수준의 기여도 추정), (ii) 채점기의 의미론적 판별력 강화(속성 존재가 아닌 동작·접근성 트리 검증), (iii) 어휘 확장 없는 신조 식별자 처리(서브워드 폴백 + BM25 가중 재조정), (iv) 실사용 텔레메트리 기반 질의 분포와 합성 태스크 분포의 정합성 측정.
