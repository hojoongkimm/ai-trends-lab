## 1. 연구 배경 및 시스템 병목 (Systems Research Problem)

코딩 에이전트가 코드를 "이해"하는 방식은 지난 2년간 거의 변하지 않았다. `grep`으로 후보를 찾고, `Read`로 파일을 열고, 호출 사슬을 머릿속에서 다시 세운다. 이 루프의 비용은 **질문의 크기가 아니라 저장소의 크기**에 비례한다. 저장소가 커질수록 같은 질문에 더 많은 탐색이 필요하고, 탐색 결과는 컨텍스트 창에 쌓여 다음 턴의 여유를 갉아먹는다.

이 저장소가 겨냥하는 병목은 네 가지다.

1. **탐색 비용과 답변 비용의 분리 실패.** 실제 벤치마크에서 그래프 없이 답한 팔은 최악의 경우 **43회의 도구 호출과 19회의 파일 읽기**를 구조를 재발견하는 데 썼다. 정답 파일 하나를 읽는 비용보다 그 파일을 찾는 비용이 압도적으로 크다.
2. **텍스트 검색의 토큰화 함정.** `switch`라는 단어를 찾으면 `LensSwitcher.swift`가 걸리지만, 그것은 `switchOrganization`에서 온 이름 충돌일 뿐 질문의 답과 호출로 연결되어 있지 않다. 반대로 `interface`에서 `impl`로 가는 동적 디스패치, 콜백, 이벤트 이미터, 프레임워크 라우팅은 grep이 따라갈 수 없는 간선이다.
3. **신선도.** 인덱스는 코드보다 늦는다. 늦은 인덱스는 없는 인덱스보다 위험하다. 에이전트는 틀린 답을 받고도 그것이 오래된 것인지 알 수 없기 때문이다. 따라서 이 시스템의 설계 문제는 "얼마나 빨리 인덱싱하는가"가 아니라 **변경과 질의 사이의 창을 어떻게 닫고, 닫히지 않은 창을 어떻게 알리는가**라는 쪽이다.
4. **출력 예산의 배분.** 검색이 정확해도 반환량이 많으면 실패한다. 컨텍스트는 유한하고, 반환된 바이트는 답이 끝난 뒤에도 창에 남는다. 그래서 "무엇을 넣을까" 다음에 반드시 "**그것들 사이에 바이트를 어떻게 나눌까**"라는 문제가 온다. 이 저장소는 그 문제를 계측 가능한 대상으로 만든다.

## 2. 아키텍처 및 수학적 정식화 (Architecture & Formulation)

### A. 추출: 파일당 한 번의 경계 통과

파이프라인은 `추출 → 저장 → 해석(resolution) → 자동 동기화`의 네 단계다. 추출 엔진은 tree-sitter 문법을 컴파일해 넣은 **네이티브 Rust 커널**이고, 입력은 `(filePath, content, language)`, 출력은 평평한 타입 버퍼(노드, 간선, 미해결 참조)다. 핵심 설계 결정은 경계 통과 횟수다. WASM 기반 파이프라인에서는 `node.kind`, `childForFieldName`, `text` 접근마다 JS와 WASM 사이를 넘기 때문에 비용의 하한이 **노드당 마샬링**이었다. 커널은 그 워크를 네이티브로 옮겨 파일당 한 번만 넘긴다.

설계 문서에 남은 스파이크 측정이 이 결정의 근거다. dubbo 저장소의 Java 파일 4,048개, 17MB, AST 노드 359만 개를 Apple M3 Pro에서 처리했을 때 다음 값이 나왔다.

| 구성 | 시간 |
| :--- | ---: |
| 기존 파이프라인 파스 루프(WASM 워커 7개, 추출·저장 디스패치 포함) | 4,700 ms |
| Rust 파스 + 워크 (rayon 병렬) | **202 ms** |
| Rust 파스 + 워크 (단일 스레드) | 1,067 ms |

네이티브 스레드 하나가 7개 WASM 워커 풀보다 4.4배 빠르고, 같은 병렬도에서는 약 14배다. 이 수치가 "추출을 네이티브로 옮긴다"는 결정을 정당화했고, 동시에 **해석·합성·프레임워크 처리·MCP는 옮기지 않는다**는 비목표를 함께 정했다. 그쪽은 마샬링 병목이 아니라 풀 병렬 작업이며, 네이티브 이득이 약 1.4배에 그치는 반면 정확성 자산(2,444개 테스트, 바이트 동일 결정성)을 걸 위험이 더 크다.

이식은 언어별 **동등성 게이트**를 통과할 때만 출하된다. 노드·간선·참조 개수가 실제 저장소 3종에서 ±0.5% 이내이고, 그 언어의 대표 흐름이 end-to-end로 연결되며, 신규 인덱싱 시간이 개선되고, 이식하지 않은 언어의 대조 저장소에 회귀가 없어야 한다. WASM 경로는 영원한 폴백으로 남아 같은 그래프를 만든다.

### B. 저장: 노드·간선·미해결 참조의 세 테이블

모든 것은 프로젝트 안의 SQLite 파일 하나(`.codegraph/codegraph.db`)에 들어간다. 스키마가 시스템의 성질을 드러낸다.

- `nodes` — `kind`, `name`, `qualified_name`, 파일 경로, 시작·끝 행과 열, docstring, signature, visibility, export/async/static/abstract 플래그, 장식자, 타입 파라미터, 반환 타입.
- `edges` — `source`, `target`, `kind`, `metadata`(JSON), `line`, `col`, `provenance`. 간선의 정체성은 5튜플 `(source, target, kind, line, col)`이고, 좌표가 없는 합성 간선까지 중복 제거되도록 `IFNULL(line, -1)` 형태의 유일 인덱스를 건다. 이 인덱스가 없던 시절 두 패스가 같은 간선을 두 번 넣어 호출자 수와 영향 범위가 부풀었다.
- `unresolved_refs` — 추출이 남긴 참조를 `pending`으로 넣고, 해석 패스가 성공하면 행을 지우고 실패하면 `failed`로 표시해 **남긴다**. 나중에 동기화에서 어떤 파일이 그 이름을 만족하는 심볼을 새로 들여오면 재시도한다. 이것이 "부분 인덱스 위에서의 점진 해석"을 가능하게 하는 장치다.
- `files` — `content_hash`, 언어, 크기, 수정 시각, 인덱싱 시각, 노드 수, 오류, 그리고 `generated` 판정. 생성 파일 판정을 인덱싱 시점에 확정해 두면 랭킹이 요청마다 파일 헤더를 읽지 않아도 된다.
- `nodes_fts` — FTS5 외부 콘텐츠 테이블과 트리거 3종으로 이름·정규화 이름·docstring·시그니처를 색인한다.
- `name_segment_vocab` — `OrderStateMachine`을 `order`, `state`, `machine`으로 쪼갠 조각을 심볼 이름과 짝지어 둔 표. FTS 토크나이저가 camelCase를 한 토큰으로 유지하므로, 자연어 프롬프트의 단어를 그래프의 심볼과 대조하려면 이 물질화된 조각 표가 필요하다. 행은 **제안**이고 조회 시점에 노드와 재검증된다.

해석은 참조 이름의 꼬리(`util.greet`의 `greet`)를 `name_tail`에 저장해 두고, import 바인딩을 거치는 참조는 모듈(`module:tag`) 아래에 주차해 둔다. 부분 인덱스들(`WHERE status = 'failed' AND reference_kind = 'imports'` 같은)은 흔한 꼬리 이름(`index`, `types`)에 대한 실패 호출이 인덱스를 지배하지 못하게 하려는 것이다.

### C. 랭킹 1단: 구조 기반 관련도 (personalized PageRank)

질의는 먼저 심볼 매칭으로 시드 집합 $S$를 만든다. 그다음 후보 부분그래프 위에서 **재시작이 있는 랜덤 워크**를 돌려 구조적 관련도를 계산한다. 갱신식은 다음과 같다.

$$
s^{(t+1)} = (1-\alpha) A D^{-1} s^{(t)} + \alpha r
$$

여기서 $A$는 무방향 인접행렬(도달 가능성을 양방향으로 본다), $D$는 차수 대각행렬, $r$은 시드 위에 균등한 재시작 벡터, $\alpha = 0.25$이며 최대 25회 거듭제곱 반복으로 수렴시킨다. 차수가 0인 노드는 질량을 잃지 않고 자기 자리에 유지한다. 간선 종류는 `calls`, `references`, `extends`, `implements`, `overrides`, `instantiates`, `returns`, `type_of`, `imports`, `navigates`의 10종만 랭킹에 쓰인다.

이 신호가 텍스트 검색이 줄 수 없는 것이다. 매칭 클러스터와 호출로 연결된 파일은 워크 질량을 얻고, 이름만 겹치는 고립된 파일은 자기 재시작 확률만 받아 0에 가까워진다. 임베딩도 없고 결정론적이며, 후보 부분그래프로 제한되므로 수백 노드 × 25회 반복으로 비용이 무시할 수준이다.

### D. 랭킹 2단: 계층 가중과 상대적 바닥

구조 신호 위에 관련도 점수가 얹힌다. 점수는 **어떻게 후보가 되었는가**와 **그것이 증거인가**를 곱으로 결합한다.

| 요소 | 값 | 의미 |
| :--- | ---: | :--- |
| 이름 지목 시드 | +50 | 호출 가능한 심볼을 이름으로 지목 |
| 질의 매칭 | +10 | 질의어가 심볼과 일치 |
| 매칭에 인접 | +3 | 1홉 이웃 |
| 주변부 | +1 (누적 상한 5) | 2홉 이상, 상한이 없으면 큰 파일이 커서만으로 관련해진다 |
| 종류 가중 | 1.0 / 약 0.5 / 0.15–0.35 | 호출 가능·타입 / 멤버 / 상수·변수·매개변수 |
| 고립 감점 | 0.08 | 약한 종류가 어떤 사용 간선도 없을 때 |
| 생성 파일 페널티 | 0.3 (저가치 0.5) | 점수와 그래프 질량 양쪽에 곱한다 |
| 상대 바닥 | 최고 점수의 20%, 1–10 사이로 제한 | 확산 질의는 넓게, 정밀 질의는 꼬리를 자른다 |

상대 바닥의 상한 10이 중요한 설계다. 하나의 직접 매칭은 결코 우연이 아니므로, 다른 곳에 점수가 몰려도 그 한 건을 배제할 수 없어야 한다. 상한이 없던 시절 이름 시드가 많은 파일 하나가 바닥을 21로 끌어올려, 에이전트가 **클래스 이름으로 지목한 파일**을 떨어뜨렸다(클래스는 +10으로 들어오고 이름 시드는 호출 가능 심볼에만 붙기 때문). 살아남은 파일이 3개 미만이면 바닥이 자른 것 중 실제 증거가 있는 것만 최소한으로 되돌린다.

저가치 판정에도 값비싼 버그가 있었다. 정규식이 `/`로 시작하는 경로에 고정되어 있어, **저장소 루트의 `test/` 디렉터리**를 잡지 못했다. 그래서 express의 라우팅 질의가 봉투의 59%를 테스트 파일 3개에 쓰고 `lib/application.js`를 잘라냈다. 정규식을 `^`에도 고정한 뒤 같은 질의가 `application.js`와 `response.js`만 반환한다.

### E. 랭킹 3단: 바이트 예산 배분

여기가 이 프로젝트에서 가장 흥미로운 부분이다. 출력 봉투는 고정이다. 작은 티어 기준 `maxOutputChars` 18,000자, 파일당 상한 3,800자, 기본 5파일, 그리고 호스트가 결과를 외부화하지 않도록 하는 **25,000자 하드 상한**이 있다. 문제는 이 상한들이 서로 합성되지 않는다는 것이었다. 실측 기준선에서 18,000자 예산에 23,193자를 배분해 **29% 초과**했고, 초과분은 25K 천장이 뒤쪽 섹션을 조용히 잘라서 흡수했다. 즉 총량 상한은 배분기가 아니라 절단기가 지키고 있었다.

할당기는 랭킹 직후, 렌더링 전에 한 번 돈다. 파일 $i$의 가중치는 다음과 같다.

$$
w_i = a_i \rho_i (1 + I_{\text{spine}}(i))
$$

$a_i$는 관련도 점수, $\rho_i$는 생성·저가치 페널티를 **두 번째로** 적용한 값이다. 랭킹이 "이 파일이 질의에 관한 것인가"를 묻는다면, 배분은 "이 바이트가 에이전트에게 무엇을 가르칠 것인가"를 묻는다. 생성된 CRUD는 도메인 단어마다 이름이 겹치고 크고 촘촘해서 정당하게 상위에 랭크될 수 있지만, 그 바이트는 기계적 상용구다. 두 번째 페널티가 그 차이를 만든다.

배분 규칙은 네 단계이고, 3단계가 쓰는 분배식은 다음과 같다.

$$
b_i = \min\left( 700 + (B - 700N) \frac{w_i}{\sum_j w_j}, 0.7B \right)
$$

여기서 $B$는 봉투 크기, $N$은 통과한 파일 수다.

1. **상대 절벽** — 최고 가중치의 15% 미만인 파일은 소스 바이트를 **0** 받는다. 경로·심볼·행 번호만 받고, 약 4,500자 대신 약 100자를 쓰며, `maxFiles` 슬롯도 소비하지 않아 그 자리가 바이트를 받을 자격이 있는 다음 파일로 넘어간다. 절벽의 비율에도 상한이 붙는다. 점수 500짜리 파일 하나가 절벽을 75로 끌어올려 방금 바닥을 통과한 모든 동료를 침묵시키면 안 되기 때문이다.
2. **바닥** — 통과한 모든 파일이 `MIN_CHARS` 700자(완전한 메서드 하나)를 먼저 받는다. 확산형 조사 질의에 퍼짐을 보장하는 부분이다.
3. **가중 분배** — 바닥을 뺀 나머지 ($B - 700N$)를 가중치 비율로 나누고, 안전 밸브로 파일당 봉투의 70%를 넘지 않게 자른다. 파일당 상한은 주 방어선에서 물러나고 안전 밸브만 남는다. 비례 분배 자체가 파일을 자기 몫으로 묶기 때문이다.
4. **예약 집행** — 이 예약이 모든 렌더 경로(전체 파일, 클러스터, 스켈레톤)를 지배한다. 예전에는 전체 파일 경로가 클러스터 경로보다 3배 후해서, 분배가 관련도가 아니라 **파일 크기**로 결정됐다. 130줄짜리 스크립트는 통째로 실려 자기 자신의 100%를 받고, 5,000줄짜리 정답 파일은 3,800자에서 잘렸다.

부수적으로 두 가지가 필요했다. 밀집한 파일에서는 모든 심볼 범위가 하나의 덩어리로 합쳐져 클러스터가 파일 전체를 덮으므로, 초과 클러스터를 **멤버 단위로** 줄여야 예약이 실제로 효력을 가진다(본문은 절대 자르지 않는다). 그리고 "도달 순서" 기반 정지 조건(`budget-90pct` 등)을 없애야 했다. 먼저 도달한 파일이 봉투를 다 쓰고 뒤의 파일이 자기와 무관한 상한에서 잘리는 구조였기 때문이다.

### F. 신선도: 디바운스, 정체성 표지, 접속 시 화해

자동 동기화는 세 겹이다.

1. **감시자 + 디바운스** — OS 네이티브 이벤트(FSEvents, inotify, ReadDirectoryChangesW)로 생성·수정·삭제를 잡고, 기본 2,000ms(환경변수로 100ms–60s) 조용해진 뒤 증분 동기화한다. 편집 폭주는 한 번으로 접힌다.
2. **파일별 정체 표지** — 디바운스 창 안에서 아직 반영되지 않은 파일을 참조하는 응답에는 `⚠️` 배너가 앞에 붙고, 에이전트에게 그 파일을 직접 읽으라고 말한다. 참조되지 않은 대기 파일은 하단 각주로 내려간다. 침묵하는 틀린 답 대신 **명시적 불확실성**을 반환하는 설계다.
3. **접속 시 화해** — MCP 서버가 (재)접속하면 첫 질의 전에 `(size, mtime)` + 내용 해시로 작업 트리와 대조한다. 서버가 없는 동안 일어난 `git pull`, 다른 편집기의 수정, 이전 세션의 변경이 다음 세션 첫 호출에서 흡수된다.

합성 간선(콜백, 이벤트 이미터, 프레임워크 라우팅)은 재구축 비용이 크므로 `CODEGRAPH_SYNTH_MIN_INTERVAL_MS`(1초–24시간)로 주기를 제한한다. 그 사이에는 합성 간선이 코드보다 뒤처질 수 있고, 도구 출력은 그 사실을 말하지 않는다는 점이 문서에 명시되어 있다.

### G. 에이전트 표면: 도구 하나

MCP 서버는 **`codegraph_explore` 하나**만 노출한다. 나머지 7개(`node`, `search`, `callers`, `callees`, `impact`, `files`, `status`)는 기능은 살아 있지만 기본적으로 목록에 오르지 않고, 그들이 돌려줄 내용은 이미 `explore` 응답 안에(영향 범위 섹션, 관계 지도, 칼리 목록) 들어 있다. 도구 메뉴가 좁을수록 오선택이 줄고 매 세션 컨텍스트를 아낀다는 것이 근거다. 사용 지침은 MCP `initialize` 응답으로 전달되고, 서브에이전트와 비 MCP 하네스를 위해 설치기가 `CLAUDE.md`·`AGENTS.md`·`GEMINI.md`·`QWEN.md`에 표식으로 감싼 짧은 절을 써 넣는다.

## 4. 한계점 및 실패 모드 (Limitations & Trade-offs)

1. **정적 분석의 지평선은 사라지지 않는다.** 런타임 동적 디스패치, DI 컨테이너, 리플렉션, 프레임워크 관례 진입점은 구조적으로 남는다. 커버리지 표의 잔차가 그것이고, 문서는 잔차를 분모 조작으로 숨기지 않는다고 명시한다. Ruby 100%와 Rust 86.7%의 차이는 언어의 정적 성질 차이다.
2. **컨텍스트 재고가 늘어난다.** 한 번의 호출로 돌려주는 밀도 높은 원문은 세션 끝까지 남아 다음 턴들의 여유를 줄인다. VS Code에서 67k 대 18k라는 값은 작은 창으로 긴 세션을 도는 사용자에게 실질적 비용이다. 처리량 지표만 보면 이 비용이 보이지 않는다.
3. **직접 질의되지 않으면 이득이 사라진다.** 에이전트가 탐색을 서브에이전트에 위임하면 그 서브에이전트는 파일을 읽고, 그래프는 오버헤드가 된다. 그래서 지침이 "탐색을 위임하지 말고 직접 답하라"고 강제한다. 즉 성능의 일부는 **프롬프트 규율**에 의존한다.
4. **합성 간선은 뒤처질 수 있고, 그 사실을 말하지 않는다.** 콜백·이벤트·프레임워크 간선의 재구축은 `CODEGRAPH_SYNTH_MIN_INTERVAL_MS`로 제한되며, 그 사이 응답은 조용히 오래된 연결을 보여준다. 일반 간선의 정체 표지(배너)와 달리 합성 간선에는 그 표지가 없다.
5. **인덱스 버전 드리프트.** 업그레이드 후 이전 버전이 만든 인덱스는 링크가 갱신되지 않는다. `codegraph status`와 첫 응답이 경고하지만, 재인덱싱은 사용자의 결정이다.
6. **단일 작성자 제약.** 프로젝트당 하나의 라이브 MCP 작성자(공유 데몬 또는 단일 직접 프로세스)만 허용된다. 두 번째 인스턴스는 작성자 잠금 오류로 종료된다. WSL2와 Windows가 같은 체크아웃을 공유하면 SQLite 잠금이 신뢰할 수 없어, WSL은 별도 인덱스(`.codegraph-wsl`)를 유지한다.
7. **잔차가 큰 언어에서는 영향 범위가 얇다.** Liquid 73.8%, Pascal 77.4%, Lua 84.2%는 "이 심볼을 바꾸면 무엇이 깨지는가"라는 질문에 대해 상당한 사각을 남긴다. Objective-C는 부분 지원이고 `.mm`(ObjC++)는 불완전하게 파싱될 수 있다.
8. **추출 커버리지가 랭킹처럼 보인다.** express의 "앱 객체가 어떻게 만들어지고 무엇을 노출하는가"는 `lib/express.js` 하나로 얇게 떨어진다. `lib/application.js`가 쓰이지 않는 파일 스코프 `var app`으로만 매칭되기 때문인데, 이는 랭킹이 아니라 추출의 빈틈이다. 저자들은 노이즈로 채우는 것보다 얇고 정확한 쪽을 택했다고 밝힌다.
9. **벤치마크는 자체 수행이다.** 4회 중앙값, 단일 질문, 자체 질의 세트이며, 비용은 `total_cost_usd`라는 실행별 값에 의존한다. 모델·하네스·질의가 바뀌면 재현되지 않을 수 있고, "88% 도구 호출 감소"는 그 7개 질문의 성질에 크게 의존한다.
10. **Rust 커널의 범위.** 커널이 담당하는 것은 문서상 20개 언어이고, 나머지는 이식 가능한 엔진이 같은 추출 로직으로 처리해 동일한 그래프를 만든다고 주장한다. 즉 "모든 언어가 네이티브"는 아니며, 성능 이득은 이식된 언어에만 해당한다.
11. **텔레메트리가 기본 켜짐이다.** 수집 항목은 도구·명령 사용과 색인된 언어의 익명 통계로 한정되고 코드·경로·심볼·질의·IP는 보내지 않는다고 명시되며, 수집 엔드포인트가 저장소 안의 공개 코드다. 그래도 기본값이 켜짐이라는 사실은 조직 환경에서 확인해야 할 항목이다. `codegraph telemetry off`, `CODEGRAPH_TELEMETRY=0`, `DO_NOT_TRACK=1`로 끈다.
12. **"100% 로컬"의 범위.** 코드와 인덱스는 로컬 SQLite에 남지만, 텔레메트리와 호스팅 플랫폼(대기자 명단)은 별개 경로다. 또한 에이전트가 MCP 도구를 통해 얻은 원문을 클라우드 모델로 보내는 것은 이 도구의 통제 밖이다.
13. **릴리스 무결성의 시점.** npm 게시는 OIDC 신뢰 게시와 provenance 증명, GitHub 번들은 SLSA v1.0 Build Level 2 증명을 갖지만, 2026년 7월 이전 릴리스는 이 파이프라인 이전이라 증명이 없다.

## 5. 연구 및 실무 활용 포인트 (Research Impact)

- **텍스트가 아니라 구조로 관련도를 매기는 방법.** personalized PageRank를 코드 그래프 위에서 α=0.25로 도는 것은, 임베딩 없이도 "이 파일이 질문의 답과 호출로 연결되어 있는가"를 결정론적으로 계산하는 값싼 해법이다. 토큰화 함정(이름 충돌)에 면역이라는 성질은 코드 검색 평가에서 재사용할 수 있는 기준선이 된다.
- **평가 지표를 처리량과 재고로 분리하기.** 도구를 반환하는 에이전트 시스템의 A/B는 대개 토큰·호출·비용·시간을 잰다. 이 프로젝트는 "답이 끝난 뒤 창에 남은 양"이라는 재고 지표를 추가하고, 그것이 처리량과 **반대 방향**으로 움직인다는 것을 측정해 공개했다. 도구 설계 평가의 일반적 교훈이다.
- **출력 예산을 1급 연구 대상으로.** 파일당 상한이 총량 상한으로 합성되지 않는다는 사실(29% 초과 배분), 도달 순서 기반 정지가 뒤 파일을 무관한 상한에서 자른다는 사실, 관련도가 아니라 파일 크기가 분배를 결정한다는 사실은 모두 계측기(`CODEGRAPH_EXPLORE_DEBUG`)를 만든 뒤에야 보였다. 계측 불가능한 것은 개선할 수 없다.
- **상대 절벽과 슬롯 이월.** 약한 파일에 소스를 주지 않고 슬롯까지 다음 파일로 넘기는 설계는, 고정 예산 아래에서 재현율과 정밀도를 동시에 다루는 깔끔한 장치다. RAG의 컨텍스트 조립 단계에 그대로 옮길 수 있다.
- **네이티브 이식의 동등성 게이트.** "바이트 동일"을 요구하지 않고 개수 ±0.5% + 검색 불변식 + 시간 개선 + 대조군 무회귀라는 4조건으로 언어별 출하를 판정하는 방식은, 대규모 추출기를 다른 런타임으로 옮길 때의 실무적 표준안이 된다.
- **불확실성의 명시.** 디바운스 창 안의 파일을 참조하는 응답에 경고 배너를 붙이고, 에이전트가 직접 읽도록 유도하는 설계는, 신선도 문제를 "더 빠르게"가 아니라 "정직하게" 푸는 접근이다.
- **도구 표면의 축소.** 하나의 강한 도구가 좁은 도구 메뉴보다 낫다는 결정은 측정된 에이전트 행동에 근거한다. MCP 서버 설계에서 도구 수를 늘리는 기본값에 대한 반례다.
- **후속 연구 방향**: (i) 동적 디스패치 커버리지를 올리는 합성 규칙의 자동 학습, (ii) 잔류 컨텍스트를 줄이면서 처리량을 유지하는 요약·압축 계층, (iii) 다중 저장소·모노레포에서의 부분 인덱스 일관성, (iv) 배분 정책의 사용자별 최적화(창 크기·모델·질의 유형), (v) 커버리지 잔차를 질의 시점에 보고하는 신뢰도 표지, (vi) PR 단위 영향 분석으로의 확장(호스팅 플랫폼이 예고하는 방향).
