## 1. 연구 배경 및 시스템 병목 (Systems Research Problem)

장기 실행 코딩 에이전트의 처리량 병목은 생성 속도가 아니라 **사람의 판단 대역폭**이다. 계획 수립, 파일 삭제, 배포, 데이터 마이그레이션처럼 되돌릴 수 없는 분기에서 에이전트는 사람의 승인을 기다리고, 그 대기는 에이전트 루프 안에서 발생한다. 운영에서 관측되는 실패 모드는 다음 세 가지다.

1. **승인의 직렬화(Blocking Gate)**: 승인 절차가 에이전트 턴 내부에 놓이면 사람의 응답 지연이 곧 턴의 wall-clock 지연이 된다. 사람이 자리에 없으면 턴은 타임아웃되거나, 기본값으로 진행되거나, 세션이 죽는다. 하루에 수십 건의 판단이 필요한 팀에서는 이 직렬화가 처리량 상한을 만든다. 프로젝트가 훅 타임아웃을 345,600초(96시간)로 잡아 둔 것은 이 병목의 크기를 그대로 드러낸다.
2. **판단 산출물의 비정형성(Unstructured Verdict)**: 채팅창의 "응 그렇게 해"는 어느 줄에 대한 지적인지, 무엇이 문제인지, 어떤 대안을 원하는지를 담지 않는다. 에이전트는 프로즈에서 의도를 재구성하고, 이 재구성이 계획 드리프트의 실제 원인이 된다. 판단의 **근거와 좌표**가 결정과 함께 전달되지 않으면 같은 왕복이 반복된다.
3. **결정의 좌표 상실(Decision-Artifact Mismatch)**: 브라우저 탭이 붙잡고 있는 것은 서버 프로세스가 만든 한 시점의 렌더링이다. 그 서버가 사라지거나 같은 포트를 새 프로세스가 점유하면(원격 모드는 고정 포트 19432를 쓰고, 로컬도 포트 재사용이 가능하다), 화면의 문서를 승인했는데 다른 문서가 승인되는 사고가 성립한다.

이 세 실패 모드는 "프롬프트로 승인 규율을 표현하려는 시도"의 구조적 한계로 정리된다. 승인은 확률적 생성 대상이 아니라 **불변식이 필요한 상태 전이**이고, 판단의 근거는 자연어가 아니라 **구조화된 좌표**이며, 대기는 턴에 종속되면 안 된다. Plannotator는 이 지점을 하네스 아키텍처 문제로 재정의한다: 리뷰하는 사람을 하네스의 한 컴포넌트로 취급하고, (i) 결정은 정확한 아티팩트 버전에 결속되고, (ii) 결정은 위치가 붙은 구조화된 근거를 나르며, (iii) 호스트가 허용하는 한 대기는 하드 블록이 아니어야 한다는 세 조건을 시스템 수준에서 강제한다.

## 2. 아키텍처 및 수학적 정식화 (Architecture & Formulation)

### A. 훅 매개 개입과 결정 프로토콜

계획 검토는 별도 명령이 아니라 호스트의 권한 요청 훅에 매달린다. Claude Code의 경우 `PermissionRequest` 훅에 `matcher: "ExitPlanMode"`를 걸고, 훅 프로세스가 표준입력으로 받은 계획을 로컬 서버가 읽어 브라우저를 열고, 사람의 결정을 훅의 JSON 응답으로 되돌린다. 응답 형태는 `hookSpecificOutput.decision.behavior`가 `allow` 또는 `deny`이고, `deny`일 때 `message`가 주석에서 합성된 피드백을 나른다.

주목할 점은 `allow` 경로다. Claude Code는 `updatedInput`이 없는 allow를 버리므로, 구현은 승인 시 **사람이 편집한 계획 본문을 `updatedInput.plan`으로 되돌려** 보낸다. 따라서 결정 함수는 단순한 이진 판정이 아니라 다음과 같은 편집 합성 연산이다.

$$
D : (p,\; A,\; e) \;\longmapsto\; (b,\; p',\; m), \qquad p' = \mathrm{apply}(p, e)
$$

여기서 $p$는 제안된 계획, $A$는 위치가 붙은 주석 집합, $e$는 사람이 삽입한 편집, $b \in \{\text{allow}, \text{deny}\}$는 행동, $m$은 $A$를 직렬화한 메시지다. 승인 이후 에이전트가 실행하는 아티팩트는 $p$가 아니라 $p'$이므로, 승인 게이트는 판정이 아니라 **공동 저작(co-authoring)** 동작이 된다. 이 성질은 "사람이 의도를 다시 설명하고 에이전트가 다시 해석하는" 왕복을 제거하며, 승인된 텍스트가 실행 텍스트와 같다는 대응 관계를 구조적으로 보장한다.

대기 모델은 호스트 버전에 따라 두 가지로 갈린다. Claude Code 2.1.287 이상에서는 계획 검토·코드 리뷰·주석 달기가 턴을 붙잡지 않고, 에이전트가 자기 턴을 끝낸 뒤 결정이 **다음 메시지로 도착**한다(`PLANNOTATOR_CLAUDE_MOD=0`으로 고전 흐름 복귀). 전자는 사람 지연을 턴 지연에서 분리하는 대신 에이전트가 문맥을 다시 진입해야 하고, 후자는 문맥 연속성을 유지하는 대신 턴을 점유한다. 이 트레이드오프는 하네스 설계에서 대기 비용을 어디에 회계할 것인가의 문제로 일반화된다.

### B. 결정 일관성의 삼중 토큰: 낙관적 동시성 제어

리뷰 표면이 "화면의 것"을 승인하도록 만들려면 세 가지 독립 질문에 답해야 한다. 누가 쓰는가(권한), 어느 버전인가(정체성), 아직 유효한가(생존성). 구현은 각각을 별도 토큰으로 분리한다.

| 토큰 | 발급 주체 | 검증 시점 | 위반 응답 |
| :--- | :--- | :--- | :--- |
| `serverSession` | 서버 프로세스 시작 시 16바이트 난수 1회 | 모든 결정 POST(승인·거부·피드백·종료) | `409 session_mismatch` |
| `planRevision` | 계획 개정마다 단조 증가 | `/api/approve` · `/api/deny` | `409 plan_revised` |
| `snapshotId` | diff 스냅샷마다 발급 | `/api/diff/fresh` · 전환·PR 전환 | 스냅샷 불일치 |

`serverSession`은 서버가 로드 시점 페이로드에 실어 보내고 탭이 결정마다 그대로 되돌려 보내는 nonce다. 고정 포트를 새 서버가 점유했을 때 남아 있던 낡은 탭은 자기 nonce를 보내고, 새 서버는 자기가 발급하지 않은 값을 보고 **아무것도 청구하거나 정산하기 전에** 거절한다. `planRevision`은 리뷰가 열려 있는 동안 계획이 개정된 경우를 잡는다. 종합하면 결정 수용 조건은 세 항의 논리곱이다.

$$
\mathrm{accept}(d) \;\Longleftrightarrow\; d.\text{nonce} = s.\text{nonce} \;\wedge\; d.\text{revision} = s.\text{revision} \;\wedge\; d.\text{snapshot} = s.\text{snapshot}
$$

여기에 하위 호환이 겹친다. `serverSession` 필드가 **없는** 요청(구버전 클라이언트, 비콘, 빈 종료 본문)은 기존대로 수용하고, **존재하는데 다른** 값만 거절한다. 이 비대칭은 마이그레이션 중 구버전 클라이언트를 깨지 않으면서 새 위험만 차단하는 선택이며, 프로토콜 진화에서 흔히 쓰이는 "결측은 통과, 불일치는 거부" 규칙의 명시적 사례다.

### C. 로컬 서버 위의 브라우저 표면

리뷰 UI는 정적 페이지가 아니라 서버 프로세스가 메모리에서 서빙하는 SPA다. 핸들러가 없는 경로는 앱 페이지를, `/assets/` 아래는 콘텐츠 해시로 명명된 청크를 메모리에서 응답한다. 모든 응답에 `nosniff`와 동일 출처 CORP가 붙고, 이미지 라우트는 `Content-Security-Policy: sandbox`를 실어 직접 열린 SVG가 스크립트를 실행하지 못하게 한다.

흥미로운 제약 하나가 설정 저장 위치를 결정했다. 각 훅 호출이 **매번 다른 랜덤 포트**에서 서버를 띄우므로, `localStorage`의 출처(스킴·호스트·포트)가 매번 달라져 설정이 유지되지 않는다. 반면 쿠키는 포트를 무시하고 호스트 단위로 스코프되므로, 설정을 쿠키에 두면 포트가 바뀌어도 살아남는다. 웹 플랫폼의 스코프 규칙 차이가 제품 제약을 그대로 결정한 사례다.

파일 접근 경계는 3단 게이트로 구현된다. (i) 동일 출처 검사, (ii) 리더 분류 — 루프백 Host, 프록시 헤더 없음, 원격 모드 아님, Codespace 아님을 모두 만족해야 "이 기계의 탭"으로 인정, (iii) 문서 유형 허용목록과 실제 경로 유형 일치 검사. 3단째가 중요한데, 이름이 `.md`인 파일이라도 실제 경로가 다른 유형이면(`key.md`가 `~/.ssh/id_ed25519`를 가리키는 식) 루트 안이라도 거절하고, 2MB 상한을 모든 리더에 적용한다.

### D. 20개 호스트 어댑터 매트릭스: N×M 통합 문제

이 저장소의 실제 부피는 리뷰 UI가 아니라 **호스트 어댑터**에 있다. 저장소에는 20개 호스트 항목이 통합 깊이에 따라 네 계층으로 등록되어 있다.

| 계층 | 호스트 | 통합 방식 | 얻는 것 / 잃는 것 |
| :--- | :--- | :--- | :--- |
| plugin (7) | Claude Code · Pi · OpenCode · DeepSeek Harness · Cline · OpenClaw · Hermes | 호스트 플러그인 API | 계획 개입 + 도구 + 답장이 다음 턴으로 도착 |
| hooks (9) | Codex · T3 Code · Qwen Code · Gemini CLI · GitHub Copilot CLI · Amp · Factory Droid · Kiro CLI · Mistral Vibe | 훅·정책·슬래시 명령 | 계획 개입은 되지만 답장 wake 의미가 호스트마다 다름 |
| mcp (2) | Cursor · 임의 MCP 에이전트 | MCP 서버만 | 끌어오기(pull) 모델, 능동 개입 없음 |
| cloud (2) | Grok Bot · Muse | 클라우드 에이전트 연동 | 세션 소유권이 원격, 로컬 게이트 불가 |

능력 행렬은 도구 제공, 답장 wake, Inbox에서 시작, 권한 카드, 계획 검토, 코드 리뷰, 주석, "이 세션에 질문"의 8개 축으로 관리되며, 각 셀의 근거가 소스 위치까지 인용된다. 27개 앱과 10개 패키지로 구성된 모노레포, 약 150k LOC, 1,782개 테스트 파일, 2025-12-28 생성 이후 228개 릴리스(약 0.7회/일)가 이 매트릭스를 유지하는 비용이다. 호스트 API가 실험적이거나 비공식인 영역(예: Codex의 훅은 Windows에서 실험적)이 많아, 어댑터 계층은 지속적인 파손 위험을 안고 있다.

### E. Inbox: 차단 게이트를 내구성 있는 큐로 전환

Inbox는 기계당 하나의 장수 로컬 서버다. 에이전트가 메시지·질문 블록·파일·가이드 리뷰를 남기고, 사람이 가능할 때 답한다. **어떤 에이전트 세션도 이 큐 때문에 열린 채 대기하지 않는다.** 답장은 질문한 세션을 그 호스트의 연결을 통해 깨우고, wake 채널이 없는 호스트는 나중에 `read_thread`로 읽는다.

어려운 부분은 저장이 아니라 **귀속(attribution)**이다. 세션 신원은 다음 우선순위로 해소된다.

$$
\mathrm{id}(s) = \text{tag} \;\succ\; \text{host env} \;\succ\; \text{clientInfo} \;\succ\; \text{thread meta} \;\succ\; \text{registry}
$$

여기서 tag는 `PLANNOTATOR_SESSION_TAG=host:id`, host env는 `PI_SESSION_ID`·`CODEX_THREAD_ID`·`QWEN_CODE_SESSION_ID`·`MUSE_SESSION_ID`·`T3CODE_THREAD_ID`, thread meta는 Codex가 모든 도구 호출에 붙이는 `_meta.threadId`, registry는 Qwen의 세션 레지스트리 파일(부모 PID 키)이다. 핵심 설계는 **모호하면 거절한다**는 것이다. 셸이 두 세션을 지목하거나 세션 없는 호스트 표식만 있으면 `session_ambiguous`, `--session`이 셸과 모순되면 `session_mismatch`로 실패하며 추측하지 않는다. 끝난 세션에 온 답장은 다른 세션에 넘기지 않는다. 잘못된 귀속이 남의 작업 공간에 답을 주입하는 것보다, 시끄럽게 실패하는 편이 낫다는 정책 선택이다.

비용도 정직하게 공개되어 있다. 컴파일된 바이너리로 실행 중인 Inbox에 대해 `read_thread`·`send_message`의 중앙값은 130–165ms이고, 그 대부분이 프로세스 기동이다. 그래서 배치 모드를 두지 않고, 대신 스크립트용 `inbox call` 서브커맨드로 한 번의 호출에 여러 동작을 처리한다.

### F. 릴리스 신뢰 체계

배포 아티팩트는 SHA256 사이드카, v0.17.2 이후 SLSA 출처 증명, CycloneDX SBOM을 갖는다. 릴리스 워크플로는 SBOM을 새 Grype 데이터베이스로 평가한 뒤에야 증명과 게시를 진행하고, 스캐너 측 무시 규칙을 거부하며, CISA KEV와 수정 가능한 Critical 판정에서 적용 가능성이 불명확한 항목을 보수적으로 런타임 취급한다. 동시에 SBOM의 범위를 **릴리스 전체 Syft 인벤토리**로 명시하고, Bun 독립 실행 파일이 번들 JS 패키지 메타데이터를 노출하지 않아 바이너리별 런타임 인벤토리가 아님을 문서에 밝힌다. 증명의 과대 해석을 스스로 차단하는 서술이다.

PR 리뷰가 이미 갖춘 성질(비동기, 라인 코멘트, 아티팩트 결속)을 로컬 에이전트 루프로 끌어내렸다는 점이 이 도구의 위치다. 반대로 PR 리뷰가 갖지 못한 성질, 즉 **승인된 텍스트가 곧 실행 입력이 되는 공동 저작**과 **턴 밖으로 꺼낸 결정 전달**을 추가했다. 수치로 확인 가능한 규모 지표는 20개 호스트 어댑터, 228개 릴리스, 1,782개 테스트 파일, 96시간 훅 타임아웃, 스크립트 호출 중앙값 130–165ms다.

## 4. 한계점 및 실패 모드 (Limitations & Trade-offs)

1. **로컬 판별의 잔여 위험**: 문서 스스로 인정하는 최대 약점이다. 프록시 표식을 붙이지 않는 포워더(생 socat, 원격 모드가 아닌 세션에 대한 SSH `-L`, Host를 루프백으로 바꾸는 nginx `proxy_pass`)는 "이 기계의 탭"으로 보인다. VS Code dev tunnel은 탐지 대상이 아니다. 즉 로컬 판별은 공격자 모델에 대한 증명이 아니라 **휴리스틱**이고, 안전한 기본값은 원격 모드(리더를 루트로 제한)를 쓰는 것이다. 반대로 원격 모드는 로그인이 없어 포트에 닿는 누구나 사용할 수 있다는 별도 위험을 진다.
2. **계층별 능력 격차**: 통합 깊이가 다르면 보장이 다르다. mcp 계층 호스트는 계획 개입도, 답장 wake도 없다. 같은 팀이 서로 다른 에이전트를 섞어 쓰면 승인 지연의 상한이 호스트별로 달라지고, 이 차이는 도구 사용자가 아니라 조직의 운영 규칙으로 메워야 한다.
3. **세션 귀속의 구조적 한계**: `/clear`나 인프로세스 `/resume`은 서버를 재시작하지 않아 이전 세션 id로 전송이 이어진다. tmux 같은 장수 프로세스가 물려받은 tag는 낡은 세션을 계속 지목한다. OpenCode는 셸에 세션 변수를 노출하지 않아 wake가 불가능하다. 신원을 환경 변수와 레지스트리에서 역추정하는 방식은 본질적으로 취약하며, 프로젝트의 답인 fail-closed는 귀속 오류를 **운영 실패로 전환**한다. 안전하지만 가용성을 지불한다.
4. **병목의 이동, 소거 아님**: Inbox는 턴 점유를 없애지만 결정을 큐로 적재한다. 우선순위·만료·재촉 같은 큐 의미론은 96시간 타임아웃 외에 없으므로, 리뷰 부채가 보이지 않는 곳에서 누적될 수 있다.
5. **보안 경계는 로컬 신뢰 가정**: 원격 모드에 인증이 없고 `0.0.0.0`에 바인딩한다. 문서가 명시적으로 경고하지만, 다중 테넌트나 인터넷 노출을 전제한 설계가 아니다.
6. **SBOM의 범위 한계**: 릴리스 전체 인벤토리이며 바이너리별 런타임 인벤토리가 아니다. 공급망 검증의 강도가 아티팩트 단위가 아니라 릴리스 단위라는 뜻이고, 이는 게이트의 해석 가능성을 낮춘다.
7. **평가 부재**: "잘못된 승인이 줄었다"는 가치 제안에 대한 공개 벤치마크가 없다. 위험도 높은 결정의 오승인률, 구조화 피드백이 계획 수렴에 미치는 토큰 절감 같은 지표는 측정되지 않는다. 아키텍처가 정교한 만큼 그 정교함의 효익은 아직 주장 수준이다.
8. **유지비의 비선형성**: 20개 어댑터 × 8개 능력 축 × 빠른 릴리스 주기(약 0.7회/일)는 조합 폭발을 만든다. 호스트 측 API 변경 하나가 매트릭스의 한 행 전체를 퇴화시키며, 그 퇴화는 사용자에게 "기능이 조용히 사라짐"으로 나타난다.

## 5. 연구 및 실무 활용 포인트 (Research Impact)

- **휴먼 인 더 루프를 런타임 1급 컴포넌트로**: 사람의 판단을 프롬프트 규율이 아니라 상태 전이로 모델링하면, 승인은 검증 가능한 사건이 된다. nonce·개정·스냅샷의 3중 토큰은 "화면의 것을 승인한다"는 요구가 있는 모든 시스템(CI 게이트, 인프라 변경, 데이터 삭제, 결제 승인)에 그대로 이식 가능한 패턴이다. 특히 **결측은 통과, 불일치는 거부**라는 하위 호환 규칙은 프로토콜 진화의 실무 표준으로 참조할 만하다.
- **승인 = 공동 저작**: `updatedInput`으로 편집본을 되돌리는 설계는 "사람이 의도를 다시 설명하는 비용"을 제거한다. 연구 질문으로는 구조화 피드백 유무에 따른 **수렴까지의 토큰·왕복 수** 비교가 자연스럽고, 이 아키텍처는 그 실험의 대조군을 쉽게 만든다.
- **대기 비용의 외생화**: 지연 결정 모드는 사람 응답 시간을 턴 wall-clock에서 분리한다. 비동기 에이전트 벤치마크에서 인간 응답 지연을 외생 변수로 놓고 처리량을 모델링할 수 있게 한다는 점에서, 평가 방법론에 직접 영향을 준다.
- **세션 신원을 프로토콜 문제로**: 이기종 호스트에서 "누가 물었는가"를 환경 변수와 파일 레지스트리에서 역추정하는 현재 방식은, 호스트가 세션 신원을 **표준으로 노출해야 한다**는 요구를 드러낸다. MCP 생태계의 실질적인 미해결 과제이며, 귀속 프로토콜 설계는 독립된 연구 주제가 될 수 있다.
- **후속 연구 방향**: (i) 리뷰 큐의 부채 동학과 우선순위 정책, (ii) 자동 승인 임계값을 위한 승인 신뢰도 캘리브레이션, (iii) 승인 경로 불변식(nonce·개정·스냅샷)의 형식 검증, (iv) 주석 기반 수렴의 정량 평가, (v) 다계층 어댑터에서 능력 격차를 사용자에게 어떻게 표면화할 것인가.
