## 1. 연구 배경 및 시스템 병목 (Systems Research Problem)

범용 코딩 에이전트(Claude Code, Codex 등)에 "리뷰 스킬"을 붙이는 방식은 데모 수준에서는 동작하지만, 수백~수천 파일 규모의 변경 집합에서 다음 세 가지 실패 모드가 반복적으로 관측된다.

1. **불완전 커버리지(Selective Skipping)**: 변경 집합이 커지면 에이전트가 암묵적으로 "일부 파일만" 리뷰하고 나머지를 누락한다. 누락 여부가 로그에 남지 않으므로 사용자는 리뷰가 완료되었다고 오인한다.
2. **위치 드리프트(Position Drift)**: 지적 내용은 타당하지만 파일/라인 좌표가 실제 결함 위치와 어긋난다. 코드 리뷰의 가치는 좌표 정확도에 직결되므로, 이 오차는 곧 신뢰도 붕괴로 이어진다.
3. **품질 분산(Quality Instability)**: 자연어 스킬 문서는 디버깅이 불가능하고, 프롬프트의 사소한 변형에도 결과가 크게 흔들린다. 재현성(Reproducibility)이 없으므로 회귀 측정도 불가능하다.

논문·도구 생태계의 관점에서 이 문제는 **"리뷰 품질을 프롬프트 제약으로 표현하려는 시도"의 구조적 한계**로 정리된다. 커버리지·좌표·룰 적용은 확률적 생성 대상이 아니라 *보장(guarantee)이 필요한 불변식*인데, 언어 모델 단일 계층에는 그 불변식을 강제할 메커니즘이 없다. `open-code-review`(이하 OCR)는 이 지점을 아키텍처 문제로 재정의한다: **반드시 틀리면 안 되는 단계는 결정론적 엔지니어링이 보장하고, 모델은 동적 판단과 문맥 검색에만 집중시킨다.** 사내에서 2년간 수만 명 규모로 운영된 뒤 공개된 도구라는 점에서, 이 설계는 벤치마크용 프로토타입이 아니라 운영 부하에서 수렴한 형태다.

## 2. 아키텍처 및 수학적 정식화 (Architecture & Formulation)

### A. 결정론적 사전 선택(Pre-dispatch Selection)과 미리보기 동치성

리뷰 파이프라인의 첫 단계는 LLM이 아니라 순수 함수다. `internal/agent/selection.go`의 `selectFiles`는 각 변경 파일에 대해 (i) 경로·확장자 허용목록 게이트, (ii) 삭제 파일 검사, (iii) 파일 단위 diff 토큰 상한을 순서대로 적용하고, 입력 순서를 보존한 채 파일별 결정을 반환한다.

$$
S = \{\, f \in \Delta \;:\; \text{gate}(f) = \text{pass} \;\wedge\; \lnot \text{del}(f) \;\wedge\; \tau(\text{diff}_f) \le L \,\}
$$

여기서 $\Delta$는 변경 파일 집합, $\tau(\cdot)$는 토크나이저 토큰 수, $L$은 `max_tokens`에서 유도된 프롬프트 상한(`llmloop.PromptTokenLimit`)이다. 이 함수는 출력·변이·git 호출·LLM 호출을 일절 수행하지 않는 순수 함수로 선언되어 있으며, 그 이유가 코드 주석에 명시되어 있다: 과거 `--preview`와 실제 실행이 각자 선택 로직을 계산하면서 결과가 어긋난 회귀(#782)를 겪은 뒤, **두 경로가 동일한 함수의 반환값을 소비**하도록 통합했다. 즉 "무엇을 리뷰할 것인가"에 대해 미리보기와 본 실행이 구조적으로 동치(preview ≡ run)이며, 실행 결과가 예고와 달라질 수 있는 항목(예산 소진, 재개 시 재사용, 제공자 장애)은 선택 단계에서 의도적으로 배제된다. 커버리지 집합은 `registerCoverage`로 봉인(seal)되어, 미리보기의 `will_review`와 실행의 실제 리뷰 집합이 같은 출처를 갖는다.

### B. 스마트 번들링: 격리된 서브에이전트로 분할 정복

선택된 파일들은 의미적으로 관련된 그룹으로 묶여 **한 번의 LLM 호출 단위**가 된다(`internal/agent/grouping.go`). 그룹 크기 상한은 `maxFilesPerGroup = 10`이고, 임계값 이하의 작은 변경 집합은 분할 자체를 생략한 단일 그룹으로 라벨링된다(이 경우 라벨은 의미를 갖지 않으며, 단지 "분할이 계산되지 않았다"는 사실만 표시한다).

설계상 중요한 두 가지 세부가 있다.

- **인덱스 기반 응답**: 그룹화 응답은 파일 경로가 아니라 파일 목록에 인쇄된 정수 인덱스를 반환한다. 경로 문자열은 길이만큼 출력 토큰을 소모하므로, 대규모 변경 집합에서 응답이 잘려 전체 집합에 대한 파일 단위 폴백으로 퇴화하던 문제를 제거했다.
- **컨텍스트 격리**: 각 번들은 독립된 서브에이전트로 실행되어 자기 컨텍스트만 본다. 이는 (i) 대규모 변경 집합에서도 단위당 어텐션 부하가 일정하게 유지되고, (ii) 자연스럽게 동시 실행이 가능하며, (iii) 한 그룹의 실패가 전체 리뷰를 오염시키지 않는 격리 경계를 만든다.

토큰 회계 관점에서 단일 거대 컨텍스트와 번들 분할의 차이는 다음과 같다. 전자는 모든 호출이 누적 이력을 재독해 비용이 $O(m^2)$로 증가하는 반면, 후자는 그룹별 1회 호출 비용의 합 $O(m)$으로 유지된다.

$$
C_{\text{single}} \approx \sum_{j=1}^{m} \tau\!\left(\bigcup_{i \le j} G_i\right) \;\;\gg\;\; C_{\text{bundle}} \approx \sum_{j=1}^{m} \tau(G_j)
$$

### C. 템플릿 엔진 기반 룰 매칭

리뷰 룰은 자연어 지시가 아니라 **경로 패턴 → 룰 문서**의 결정론적 매핑으로 해석된다. `internal/config/rules/system_rules.json`은 기본 룰(`default.md`)과 65개의 경로 패턴 매핑을 담고 있으며, 대응하는 룰 문서 64개가 저장소에 내장된다(언어별: Java, Go, Kotlin, Rust, C/C++, C#, Python, PHP, Swift, TypeScript/JS, Scala, Haskell, Nim, Julia, R, Terraform, Bicep, Nix, GraphQL, Protobuf 등 / 파일 성격별: 빌드 파일 `pom.xml`·`build.gradle`·`package.json`·`Cargo.toml`, CI 워크플로, 템플릿 엔진 계열, `.properties`, `mapper/dao` XML 등). 확장자가 없는 파일은 첫 줄을 스니핑해 Objective-C와 Mathematica 같은 모호한 경우를 판별한다(`sniffer.go`).

이 구조의 효과는 정밀도가 아니라 **검증 가능성**에 있다. 룰 적용 결과가 결정론적이므로, "룰 문서 표가 모든 시스템 룰 패턴을 매칭 순서대로 나열하는가"를 단위 테스트로 고정할 수 있다(`rule_docs_table_test.go`). 자연어 룰 가이드에서 흔히 발생하는 "문서에 있는 룰이 실제로는 적용되지 않는" 드리프트가 구조적으로 차단된다.

### D. 외부 포지셔닝·리플렉션 모듈과 비동기 후처리

지적의 좌표 정확도와 내용 정확도는 생성 단계가 아니라 **후처리 단계**에서 별도 모듈로 보정된다. `reviewtask.CommentWorkerPool`은 고정 크기 워커 풀(기본 8)로 라인 범위 추적(line-range tracking), 재추적(re-tracking), 리플렉션(reflection), 수정 제안 검증(suggestion validation)을 비동기로 처리한다. 이들을 메인 LLM 툴 루프에서 분리한 이유는 명시적이다: 후처리가 툴 루프를 점유하면 전체 지연이 증가하기 때문이다. 풀은 키(subtask) 단위로 대기 그룹을 분리해, 다른 하위 작업의 제출과 경쟁하지 않고 특정 단위만 드레인(drain)할 수 있다.

### E. 시나리오 튜닝 툴셋과 2단계 프롬프트

에이전트에 제공되는 도구는 7개로 고정되어 있다: `task_done`, `code_comment`, `file_read`, `file_find`, `file_read_diff`, `code_search`(그리고 미지정 이름을 위한 `unknown`). 범용 에이전트 툴킷(수십 개 스키마)과 달리, 리뷰 과업에서의 호출 빈도 분포·도구별 반복률·신규 도구가 전체 호출 체인에 미치는 영향을 대규모 운영 트레이스로 분석해 **목적 특화 최소 집합**으로 정리했다. 프롬프트 역시 파일별 PLAN 단계와 MAIN_TASK 툴 사용 단계의 2단 구조로 분리되어 있으며, 툴 루프는 컨텍스트 압축 정책(`CompressionPolicy`)과 유예 정책(`GracePolicy`)을 가진 `llmloop.Task`로 캡슐화된다.

비용 사전 추정은 코드에 상수로 고정된 근사식이다: 호출당 프롬프트 오버헤드 2,000 토큰, 파일당 MAIN_TASK 라운드 7회, 라운드당 출력 700 토큰.

$$
\hat{T}_{\text{total}} = \sum_{f \in S} \Bigl( 2000 + 7 \cdot \bigl( \tau(\text{diff}_f) + 700 \bigr) \Bigr)
$$

주석은 이 값을 **비용 추정의 하한(floor)으로** 규정한다. 툴 사용이 프롬프트를 증폭시킬 수 있고, 실제 사용량은 API 응답의 usage로만 확정되기 때문이다. 이 겸손한 회계 태도는 벤치마크 해석에도 그대로 적용된다.

### F. Delegation Mode: 결정론 계층만 제공하는 분리 실행

OCR은 자체 LLM 자격증명 없이도 동작하는 **위임 모드**를 제공한다. `ocr delegate preview`가 검토 대상 파일 목록·제외 사유·ref 메타데이터를 JSON으로 산출하고, `ocr delegate rule`이 파일 집합을 동일 룰 그룹으로 묶어 마크다운으로 출력하면, 실제 리뷰는 호스트 에이전트(Codex, Claude Code 등)가 자기 모델과 도구로 수행한다. 즉 파이프라인을 **"결정론 계층(파일 선택 + 룰 해석)"과 "생성 계층(추론)"으로 절단**해, 전자만 이식 가능한 모듈로 제공하는 셈이다. 이 분리는 비용 구조에도 영향을 준다: OCR 쪽 API 비용이 0이 되는 대신, 호스트 모델의 컨텍스트 예산을 리뷰가 직접 소모한다.

## 3. AACR-Bench 기반 정량 비교 (Comparative Benchmark)

평가셋은 **인기 오픈소스 저장소 50개, 실제 Pull Request 200건, 10개 프로그래밍 언어, 80명 이상의 시니어 엔지니어 교차 검증(주석된 정답 결함 1,505건)으로** 구성되며, 데이터셋은 Hugging Face(`Alibaba-Aone/aacr-bench`)에 공개되어 있다. 지표는 정밀도(보고된 지적 중 실제 결함 비율), 재현율(1,505건 중 발견 비율), F1, 리뷰당 평균 시간·토큰이다.

| 수행 주체 (모델) | F1 | Precision (TP/보고) | Recall (TP/1,505) | 평균 시간 | 평균 토큰 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **OCR** (Claude-4.6-Opus) | **25.10%** | **33.90%** (301/889) | 20.00% | **1m23s** | **385K** |
| **OCR** (Qwen3.8-Max) | 23.00% | 33.90% (262/774) | 17.40% | 5m14s | 334K |
| **OCR** (GLM-5.2) | 21.30% | 32.30% (239/741) | 15.90% | 7m58s | 682K |
| **OCR** (GPT-5.5) | 21.00% | 32.10% (234/728) | 15.50% | 2m51s | 422K |
| **OCR** (Claude-4.8-Opus) | 17.90% | **37.80%** (176/465) | 11.70% | 1m06s | 352K |
| Claude Code (Claude-4.6-Opus) | 11.57% | 7.23% (435/5,980) | **28.90%** | 13m06s | 5,664K |
| Claude Code (Qwen3.7-Max) | 12.17% | 8.23% (351/4,260) | 23.37% | 8m06s | 5,153K |
| Claude Code (GLM-5.1) | 11.93% | 8.37% (313/3,742) | 20.80% | 14m10s | 4,038K |
| Codex (GPT-5.5) | 8.36% | 27.82% (74/266) | 4.92% | 2m58s | 525K |

동일 모델(Claude-4.6-Opus) 비교에서 F1은 11.57% → 25.10%로 2.2배, 정밀도는 7.23% → 33.90%로 4.7배 상승한다. 반면 토큰은 5,664K → 385K로 약 1/14.7이며, 공식 사이트는 1,000 PR 기준 절감률을 **1/9**로 표기한다. 시간도 13분 대에서 1분 23초로 줄어 CI 지연 관점의 이득이 크다.

주목할 점은 **재현율의 역전**이다. 최고 재현율은 Claude Code(Claude-4.6-Opus)의 28.90%로, OCR의 최고치(20.00%)보다 8.9%p 높다. 즉 이 아키텍처는 "더 많이 찾는" 방향이 아니라 **"보고한 것 중 실제 결함 비율"을 극대화하는 방향**으로 최적화되어 있다. 보고 건수가 5,980건에서 889건으로 줄고 그중 참인 비율이 7.23%→33.90%로 오르는 구조는, 리뷰어의 트리아지 비용(거짓 경보 처리 시간)을 1차 목적함수로 둔 설계 선택과 정확히 일치한다.

## 4. 한계점 및 실패 모드 (Limitations & Trade-offs)

1. **재현율 상한의 구조적 수용**: 정밀도 우선 정책은 필연적으로 미탐을 남긴다. 벤치마크 상 최고 재현율(28.90%)조차 결함의 3/4을 놓치는 수준이며, 보안 결함이나 데이터 손상 경로처럼 미탐 비용이 큰 영역에서는 이 트레이드오프가 부적절할 수 있다. 정밀도·재현율을 단일 F1으로 요약하는 관행 자체가 이 도구의 목적에는 맞지 않는다.
2. **벤더 자체 벤치마크의 외적 타당성**: AACR-Bench는 도구 개발 주체가 구축·공개한 평가셋이다. 평가 대상 PR이 리뷰 룰과 정답 주석의 설계 가정에 노출되어 있을 가능성(벤치마크 오염), 80명 이상의 주석자 간 합의도(inter-annotator agreement)가 공개되지 않은 점, 표에 보고된 단일 실행 결과의 분산(seed·모델 스냅샷·temperature)이 제시되지 않은 점은 외부 재현 없이는 해소되지 않는다.
3. **룰 기반 매칭의 표현력 한계**: 경로·확장자 기반 룰 선택은 누락이 없고 예측 가능하지만, 아키텍처 수준의 결함(경계 위반, 트랜잭션 경계, 상태 기계 오류, 성능 회귀)은 어떤 파일 패턴에도 매핑되지 않는다. 이 계층은 "패턴으로 표현 가능한 결함"에만 작동하며, 그 외는 전적으로 에이전트의 자유 탐색에 의존한다.
4. **LLM 그룹화의 잔여 확률성**: 파일 선별은 결정론적이지만 번들 분할은 LLM이 수행한다. 그룹 라벨은 비결정적이며, 응답 절단 시 폴백 경로가 존재한다. 즉 "결정론 + 에이전트 하이브리드"의 결정론 보장은 선택·룰 계층에 한정되고, 분할·지적 생성·후처리 보정은 여전히 모델 분산에 노출된다.
5. **비용 추정의 비보수성**: 추정식은 툴 사용 증폭을 반영하지 못하는 하한이며, 대규모 리뷰에서 예상 비용을 과소평가할 수 있다. 또한 번들 동시 실행은 제공자 속도 제한(rate limit)과 상호작용해 지연 분산을 키운다.
6. **좌표 정확도의 잔여 오차**: 외부 포지셔닝 모듈이 후처리로 보정하지만, 리팩터링으로 diff 헝크 경계가 이동한 경우 라인 재추적이 실패할 수 있고, 그 실패는 조용히 발생한다(리뷰 결과에는 지적이 남고 좌표만 어긋남).
7. **언어별 깊이 불균형**: 룰 문서 수와 성숙도가 언어마다 다르다. 주력 언어(Java, Go)와 주변 언어(Nim, Haskell 등)의 실제 커버리지 품질 차이는 벤치마크의 언어별 분해 없이는 판단할 수 없다.

## 5. 연구 및 실무 활용 포인트 (Research Impact)

- **에이전트 하네스 설계의 일반 원리**: "정확성이 요구되는 단계는 결정론적으로, 판단이 필요한 단계만 모델에" 위임하는 절단면(cut) 설계는 코드 리뷰를 넘어 데이터 검증·마이그레이션·문서 생성 등 모든 고위험 자동화에 이식 가능한 패턴이다. 특히 *미리보기와 실행의 동치성*을 순수 함수 하나로 강제하는 기법은, 에이전트 시스템에서 흔한 "계획과 실행의 괴리"를 구조적으로 제거하는 표준적 해법이 될 수 있다.
- **평가 프로토콜 설계**: 정밀도·재현율·시간·토큰을 분리 보고하고, "보고 건수(TP+FP)"를 함께 공개하는 형식은 LLM 리뷰어 비교 연구에서 필수적이다. F1 단일 지표는 정밀도 우선 설계와 재현율 우선 설계를 구분하지 못한다.
- **CI 통합과 게이트 설계**: `--fail-on-severity`에 해당하는 임계값 정책, 세션 재개(`--resume`)를 통한 중단 복구, JSON 출력 기반의 상위 오케스트레이션은 리뷰를 "제안"이 아니라 "정책 집행"으로 운용하는 경로를 제공한다. 정밀도가 높은 도구는 게이트로, 재현율이 높은 도구는 사전 스크리닝으로 배치하는 **앙상블 운용**이 실무적으로 합리적이다.
- **후속 연구 방향**: (i) 정밀도 우선 파이프라인에 재현율 회수 계층을 추가하는 하이브리드(예: 결정론 룰 → 에이전트 → 별도 재현율 특화 스윕), (ii) 지적별 신뢰도 캘리브레이션과 그에 기반한 임계값 자동 선택, (iii) 위치 정확도를 별도 지표로 측정하는 벤치마크 확장, (iv) 번들 분할 정책의 최적화(의미 응집도와 컨텍스트 비용의 다목적 함수).
