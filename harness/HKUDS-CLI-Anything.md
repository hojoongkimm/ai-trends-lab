## 1. 연구 배경 및 시스템 병목 (Systems Research Problem)

에이전트가 실제 소프트웨어를 못 쓰는 이유는 추론 능력이 아니라 **인터페이스의 성질**이다. 이 저장소의 논지는 GUI가 인간에게 잘 맞춰진 표면이라는 데서 출발한다. 픽셀로 상태를 압축하고, 포인팅과 포커스에 의존하고, 프로젝트 그래프를 숨기고, 연속적 지각을 전제한다. 에이전트에게 필요한 것은 정반대다. 안정된 동사, 명시적 상태, JSON, 내구성 있는 이력, 프로그램적 검증, 설치 가능한 도구, 그리고 과업 시점의 발견 경로다.

1. **제어 표면의 불일치(Control-Surface Mismatch)**: 스크린샷 해석과 좌표 클릭은 인터페이스 변경에 취약하고, 타이밍 의존적이며, 같은 의도를 여러 궤적으로 흩뿌린다. 학습과 계획 모두에게 나쁘다.
2. **기능 보존의 실패(Capability Loss)**: API 래퍼는 원 소프트웨어의 기능 대부분을 잃고, 단순 재구현은 "장난감"이 된다. GUI 자동화는 유지비가 높고, MCP 서버가 없는 소프트웨어도 많다.
3. **검증의 비대칭(Verification Asymmetry)**: 최종 산출물은 구조화되어 쉽게 검사되는데, 그 산출물을 만드는 경로만 픽셀 관측과 클릭으로 규정된다. 검사할 수 있는 것은 만들 수도 있어야 한다는 것이 논문의 핵심이다.
4. **발견과 설치(Discovery)**: 좋은 하네스도 에이전트가 찾아서 설치하고 사용법을 읽지 못하면 없는 것과 같다.

응답은 네 층이다. **생성 SOP**(7단계), **계약**(6튜플), **검증**(4계층 테스트), **유통**(CLI-Hub). 각 층이 독립적으로 쓸 수 있다는 점이 실용적 강점이다.

## 2. 아키텍처 및 수학적 정식화 (Architecture & Formulation)

### A. 계약: 여섯 성분과 여섯 불변식

논문은 하네스를 실제 소프트웨어 백엔드 위의 계약 $H=(S, C, I, R, V, D)$로 정의한다.

| 성분 | 내용 | 저장소 구현 |
| :--- | :--- | :--- |
| $S$ | 지속 상태 공간 | 프로젝트 JSON, 세션 파일, undo/redo, 미리보기 상태 |
| $C$ | 명령 어휘 | 도메인 변이·프로브, Click 서브커맨드와 REPL |
| $I$ | 검사 표면 | `--json` 상태·목록·정보·스키마·이력 |
| $R$ | 렌더·내보내기 관계 | 실제 바이너리 호출(`libreoffice --headless`, `blender --background`, `melt`) |
| $V$ | 검증 계층 | 단위·E2E·서브프로세스·파일 형식·픽셀·미디어 검사 |
| $D$ | 발견 계층 | `SKILL.md`, 레지스트리 메타데이터, 설치 전략, CLI-Hub |

계약이 유용한 이유는 소프트웨어별 의미와 에이전트 대상 불변식을 분리하기 때문이다. Blender 장면, Draw.io 그래프, LibreOffice 문서는 $S$와 $C$가 전부 다르지만 같은 불변식을 만족해야 한다. 논문이 제시하는 여섯 가지는 명시적 상태, 타입 있는 행동, 값싼 검사, 백엔드 진실, 프로그램적 검증, 발견 가능성이다. 이 중 어느 하나라도 빠지면 하네스는 "명령을 감싼 얇은 껍데기"로 퇴화한다.

불변식은 술어로 읽을 수 있다. 예를 들어 백엔드 진실 조건은, 산출물 $o$가 존재하고 사용자가 열 수 있는 형식일 것을 요구한다.

$$
\mathrm{truth}(o) = \exists o \in \mathrm{Outputs} : \mathrm{magic}(o) = \mathrm{expected} \wedge \lvert o \rvert \gt 0
$$

종료 코드 0은 이 술어의 대체물이 아니다. 논문이 반복해서 강조하는 실패 모드가 정확히 그것이다. 백엔드 프로세스는 성공적으로 종료되고 아무것도 만들지 않을 수 있다.

### B. 일곱 단계 생성 SOP

`cli-anything-plugin/HARNESS.md`(747줄)가 방법론의 원본이다.

| 단계 | 하는 일 | 산출물 |
| :--- | :--- | :--- |
| 1 | 코드베이스 분석: 백엔드 엔진, GUI→API 매핑, 데이터 모델, 기존 CLI, undo/redo | 인터페이스 지도 |
| 2 | CLI 설계: REPL·서브커맨드 이중 모드, 명령 그룹, 상태 모델, `--json` | 명령 트리 설계 |
| 3 | 구현: 데이터 계층 → 프로브 → 변이 → 백엔드 래퍼 → 세션 → REPL | 설치 가능 패키지 |
| 4 | 테스트 계획(`TEST.md` 1부): 파일별 예상 테스트 수 | 계획 문서 |
| 5 | 테스트 구현: 4계층 | 테스트 코드 |
| 6 | 테스트 문서(`TEST.md` 2부) | 결과 기록 |
| 6.5 | `SKILL.md` 생성: Click 데코레이터·setup.py·README에서 메타데이터 추출 | 에이전트용 스킬 |
| 7 | PyPI 게시 | `pip install cli-anything-<software>` |

가장 강한 규칙은 1번이다. **실제 소프트웨어를 쓰고, 재구현하지 말 것.** Pillow로 GIMP를 흉내내거나 bpy 스크립트를 만들고 Blender를 부르지 않는 것이 안티패턴으로 명시된다. 대신 유효한 중간 파일(ODF, MLT XML, SVG)을 생성하고 실제 애플리케이션에 넘긴다. 소프트웨어는 **필수 의존성**이며, 없으면 테스트는 건너뛰지 않고 실패한다.

두 번째 함정은 **렌더링 갭**이다. 프로젝트 파일만 조작하면 효과가 렌더에 반영되지 않을 수 있다. 처방은 우선순위가 있는 세 단계다. 원 엔진(MLT 프로젝트에 `melt`) → 필터 번역 계층(MLT 필터를 ffmpeg `-filter_complex`로) → 수동 렌더 스크립트. 번역 계층에는 중복 필터 병합, 인터리브 순서, 파라미터 스케일 차이, 매핑 불가 효과라는 구체적 함정 목록이 붙는다. 타임코드 정밀도도 별도 규칙이다. 29.97fps에서 `int()` 대신 `round()`, 표시에는 정수 산술, ±1프레임 허용.

### C. 이중 출력: 한 명령, 두 독자

모든 명령은 사람용 표와 기계용 JSON을 함께 낸다. 전역 `--json` 플래그가 출력 표현을 바꾸고, 명령 자체는 하나다.

```text
cli-anything-blender --project scene.blend-cli.json --json object add cube --name Body
cli-anything-blender --project scene.blend-cli.json object add cube --name Body
```

이 설계의 효과는 검증 비용이다. 사람이 읽는 경로와 에이전트가 읽는 경로가 같은 실행을 공유하므로, JSON 검증이 곧 사람 경로의 검증이 된다. 별도 API 계층을 두면 두 경로가 서로 다른 코드를 타고 조용히 갈라진다.

상태는 1급 표면이다. 프로젝트 JSON이 작업 공간이고, 세션 파일이 현재 프로젝트·수정 상태를 기록하며, undo/redo 스택이 탐색을 복구 가능하게 만든다. 동시 쓰기 손상을 막기 위해 세션 저장은 배타적 파일 잠금을 쓴다(`"r+"`로 열고, 잠그고, 잠금 안에서 잘라 쓰기). 인자 없이 실행하면 REPL로 들어간다. Click의 `invoke_without_command=True`로 구현되고, 모든 하네스가 같은 `repl_skin.py`를 복사해 배너·프롬프트·이력·진행 표시를 공유한다.

### D. 검증: 네 계층과 산출물 술어

| 계층 | 검사 대상 | 예시 |
| :--- | :--- | :--- |
| 단위 | 합성 데이터 위 핵심 함수 | 프로젝트 생성, 레이어 연산, 필터 파라미터 |
| E2E 네이티브 | 프로젝트 파일 생성 파이프라인 | ODF ZIP 구조, MLT XML, SVG 정합성 |
| E2E 실제 백엔드 | 실제 소프트웨어 호출과 산출물 | LibreOffice PDF의 `%PDF-` 매직바이트, Blender 렌더 PNG |
| CLI 서브프로세스 | 설치된 명령 자체 | `cli-anything-gimp --json project new`의 JSON 유효성 |

영상·음성은 프레임과 스펙트럼으로 검증한다. 페이드인은 0번 프레임이 거의 검정인지, 중간 프레임의 밝기·채도가 소스와 어떻게 다른지, 레터박스·필러박스 검정 픽셀을 제외하고 비교하는지까지 규칙으로 적혀 있다. 오디오는 시작·끝의 RMS와 스펙트럼을 본다. 이 수준의 검증을 요구하는 이유는 앞의 술어와 같다. "명령이 0을 반환했다"는 증거가 아니다.

공개된 테스트 집계는 30개 하네스 행의 합이 2,622건이고, 표의 TOTAL 줄은 2,464, 배지는 2,461, 기능 소개 문장은 2,280+로 적혀 있다. 네 숫자가 서로 다르다는 점은 4절에서 다룬다.

### E. 미리보기: 표시를 프로토콜로 분리

에이전트도 시각 피드백이 필요하고 사람도 산출물을 봐야 한다. 문제는 그 중간 상태를 어떤 계약으로 나르는가다. CLI-Anything은 GUI 스트리밍 대신 **디스크 번들**을 쓴다. `manifest.json`, `summary.json`, `artifacts/`가 기본이고, 라이브 워크플로는 `session.json`(현재 헤드)과 `trajectory.json`(명령→미리보기 이력)을 더한다. 프로토콜 버전은 `preview-bundle/v1`, 궤적은 `preview-trajectory/v1`이다.

생산자/소비자 분리가 핵심이다. 하네스는 `cli-anything-preview`로 번들을 **발행**하고, CLI-Hub는 `cli-hub previews inspect|html|watch|open`으로 이미 발행된 것을 **읽기만** 한다. 도메인 진실은 하네스 안에 남고, 뷰어는 CAD·영상·3D·GPU 캡처·다이어그램에 걸쳐 일반화된다.

캐시 키는 소스 지문의 해시다. 프로젝트 JSON을 정규화해 SHA-256을 취하고, 소프트웨어·레시피·번들 종류·옵션·프로토콜 버전과 함께 다시 해시해 캐시 키를 만든다.

$$
k = \mathrm{SHA256}\left(\mathrm{canon}\left(f_{\text{source}}\right) \Vert \text{software} \Vert \text{recipe} \Vert \text{protocol} \Vert \text{options}\right)
$$

충실성이 설계 제약이다. 장난감 렌더러와 화면 스크레이핑은 미리보기 진실의 출처로 명시적으로 거부된다. 시각화를 위해 임시 카메라나 조명을 넣었다면 번들이 그 한계를 표시하고 설명해야 한다. 현재 미리보기 지원 통합은 5개다(Shotcut, Openscreen, Blender, FreeCAD, RenderDoc).

### F. 두 가지 성장 모드: 백엔드를 찾는 경우와 만드는 경우

**Blender는 백엔드가 이미 성숙한 경우다.** bpy, RNA 속성, 오퍼레이터, 의존성 그래프, 렌더 엔진이 그대로 노출되어 있어 하네스는 그 위에 얹히면 된다. 현재 명령 트리는 12개 그룹 노드(루트와 라이브 미리보기 중첩 포함)에 54개 명령 함수(공개 53, 숨김 모니터 1)를 갖고, 수정자 8종을 타입 있는 파라미터와 범위로 정의한다. 작업 상태는 이진 `.blend`가 아니라 에이전트가 검사할 수 있는 `.blend-cli.json`이고, 네 단계 사상이 이를 실제 렌더로 잇는다. 명령이 JSON 계약을 변이하고, 도메인 모듈이 개념을 검증하고, 하향 패스가 완전한 bpy 스크립트를 만들고, 백엔드 래퍼가 실제 Blender를 돌려 산출물 존재를 확인한다. 래퍼는 프레임 번호 접미사를 해석하고, EEVEE의 버전 차이(`BLENDER_EEVEE_NEXT` 대 `BLENDER_EEVEE`)를 흡수한다. 테스트는 208건이다.

**Slay the Spire II는 백엔드가 없어서 만든 경우다.** 유용한 상태가 실행 중인 게임 프로세스 안에 있고, 백엔드 객체와 화면 노드에 흩어져 있다. 하네스는 프로세스 **안**에 작은 브리지를 심는다. Godot 메인 루프에 붙어 `ProcessFrame`에 큐를 연결하고, `localhost:15526`에 `HttpListener`를 열고, 프레임 소유 객체에 접근해야 하는 작업을 `RunOnMainThread`로 넘긴다. 큐는 프레임당 최대 10개를 처리하고 예외를 요청에 붙여 돌려준다. 표면은 28개 Click 명령, 15개 정규화 결정 상태, 24개 행동 동사로 좁혀진다. 게임은 여전히 시뮬레이션의 권위자다.

이 대비가 논문의 교육적 핵심이다. 키–마우스 제어는 저수준 운동 인터페이스이고, 같은 의도("카드 하나를 몬스터 하나에")가 수많은 궤적으로 실현된다. 커서 경로, 호버 상태, 클릭 타이밍, 드래그 제스처, 해상도, 애니메이션 지연이 모두 다르고, 학습자는 그 우연한 변이를 모델링하느라 용량을 쓴다. CLI 행동은 그 동치류를 하나의 명령으로 접는다.

$$
\phi : \lbrace \text{traces} \rbrace \to \lbrace \text{actions} \rbrace, \qquad \lvert \mathrm{Im}(\phi) \rvert \ll \lvert \mathrm{dom}(\phi) \rvert
$$

사상 $\phi$의 상이 작다는 것이 곧 계획 공간과 데이터 수집 단위가 작다는 뜻이다.

### G. 유통과 실사용 신호

CLI-Hub는 패키지·레지스트리 층이다. 설치기는 pip, npm, uv, 번들·시스템 도구, 명령 기반 설치를 정규화하고, 목록·검색은 JSON을 지원한다. 현재 저장소의 `registry.json`은 79개 항목, `public_registry.json`은 서드파티 18개, 동반 스킬은 71개다.

논문이 공개한 사용 신호는 흥미롭다. CLI-Hub 텔레메트리에서 **에이전트 호출 비중 87.8%**, 에이전트/인간 호출 비율 **7.19배**다. 이 저장소가 이미 인간용 패키지 브라우저가 아니라 런타임 의존성으로 쓰이고 있다는 뜻이고, 그래서 다음 단계가 "에이전트 우선 Hub API"라는 결론으로 이어진다.

## 3. 구조적 비교 (Comparative Positioning)

| 항목 | GUI 에이전트 | API 래퍼 | MCP 서버 | CLI-Anything 하네스 |
| :--- | :--- | :--- | :--- | :--- |
| 제어 표면 | 픽셀·좌표 | 원 서비스 엔드포인트 | 도구 호출 | 상태 있는 CLI |
| 상태 | 화면에 암묵 | 요청 단위 | 세션 의존 | 프로젝트·세션·undo 파일 |
| 기능 보존 | 높음(불안정) | 낮음~중간 | 부분 | 실제 바이너리 경유 |
| 검증 | 스크린샷 비교 | 응답 스키마 | 도구 응답 | 매직바이트·픽셀·RMS·구조 |
| 설치 | 브라우저·RPA 스택 | SDK | 호스트 설정 | `pip install` |
| 발견 | 없음 | 문서 | 서버 목록 | `SKILL.md` + 레지스트리 |

같은 하네스 카테고리의 다른 문서와 비교하면 목표가 다르다. `affaan-m/ECC`는 한 에이전트의 작업 절차와 기억을 최적화하고, `NVIDIA/SkillEvaluator`는 스킬의 한계 기여를 측정한다. CLI-Anything은 **소프트웨어 쪽 인터페이스**를 바꾼다. 에이전트를 잘 쓰게 만드는 대신, 소프트웨어를 에이전트가 쓸 수 있게 만든다. 그래서 이 저장소의 산출물은 프롬프트가 아니라 69개의 pip 패키지다.

## 4. 한계점 및 실패 모드 (Limitations & Trade-offs)

1. **리프팅할 수 없는 소프트웨어가 있다**: 컴파일된 바이너리만 있고 상태가 불투명하거나, 헤드리스 모드에서 렌더가 불가능하거나, 픽셀로만 결과를 관측할 수 있는 경우. 논문도 범위를 인정하고, 그런 경우 접근성 API·GUI 자동화가 여전히 필요하다고 적는다.
2. **미리보기 커버리지가 얇다**: 지원 통합이 5개이고, 논문 스스로 "의미 있는 시각 상태에 대한 커버리지가 아직 불완전하다"고 말한다. 미리보기가 없는 하네스는 상태 JSON만으로 판단해야 한다.
3. **과업 성공 벤치마크가 없다**: 평가는 카탈로그 규모, 사용량, 생태계 성숙도다. "에이전트가 이 하네스로 사용자의 과업을 실제로 완수하는가"를 재는 과업 수준 벤치마크는 다음 연구 과제로 남아 있다. 테스트 수는 신뢰의 대리 지표이지 과업 성능이 아니다.
4. **수치 드리프트가 이미 있다**: 테스트 수가 배지 2,461, 표 합계 2,622, TOTAL 줄 2,464, 기능 문장 2,280+로 네 가지다. 논문의 카탈로그 스냅샷(65/18/61/5)도 현재 저장소(79/18/71)보다 오래됐다. 규모를 자랑하는 프로젝트에서 수치 신뢰도는 곧 감사 가능성이다.
5. **백엔드 의존성이 CI를 막는다**: 실제 소프트웨어가 없으면 테스트가 실패한다는 규칙은 정직하지만, 그만큼 CI에서 전체 스위트를 돌리기 어렵다. 실제로 여러 하네스가 백엔드 게이트로 E2E를 건너뛰고, 그 수가 표에 섞여 있다.
6. **모노레포의 유지비**: 69개 패키지, 1,872개 파일, 98 MB 체크아웃. 하네스마다 테스트·문서·스킬 사본이 따로 있고, 스킬은 정본과 패키지 내 사본 두 곳에 존재한다. 사본 부패는 구조적 위험이다.
7. **Hub가 아직 인간 지향이다**: 논문 스스로 "현재 CLI-Hub는 부분적으로 인간 지향"이라고 밝힌다. 에이전트가 능력 검색·설치 계획·상태 진단을 구조화된 형태로 조회하는 API는 아직 없다.
8. **실행 표면이 곧 위험 표면이다**: 하네스는 실제 애플리케이션을 실행하고 파일을 쓴다. 경로 탈출·심볼릭 링크 하드닝 같은 사례가 뉴스에 보이는 것은 성숙의 신호이자, 각 하네스의 입력 검증이 계속 관리되어야 한다는 뜻이다. 문서 파싱은 `defusedxml`로 일원화하는 정리가 그 대응이다.

## 5. 연구 및 실무 활용 포인트 (Research Impact)

- **인터페이스 선호가 성능을 바꾼다**: SWE-agent가 에이전트-컴퓨터 인터페이스의 유용성을 보였듯, 같은 모델이 GUI와 CLI에서 다른 성과를 낸다는 것은 능력이 아니라 표면의 함수다. 이 저장소는 그 명제를 데스크톱 소프트웨어 전반으로 확장하는 실증 재료를 제공한다.
- **검증 대칭의 원리**: 산출물을 코드로 검사할 수 있다면, 그 산출물은 코드로 만들 수 있어야 한다. 이 원리는 벤치마크 설계에 직접 쓸 수 있다. 검사 가능한 산출물(문서, 도표, 영상 컷, CAD 모델)을 요구하는 과업은 픽셀 과업이 아니라 실행 환경 과업으로 재정의된다.
- **동치류로 접는 행동 공간**: 궤적을 의미 행동으로 사상하면 계획 공간과 데이터 수집 단위가 함께 줄어든다. 이 관점은 GUI 데모 수집 비용을 낮추는 실무적 경로이자, 행동 추상화 수준이 학습 효율에 미치는 영향을 재는 연구 질문이다.
- **계약으로서의 하네스**: 6튜플은 새 소프트웨어를 리프팅할 때 빠진 성분을 빠르게 진단하는 체크리스트로 쓸 수 있다. 상태가 없으면 세션을, 검사가 없으면 `--json`을, 발견이 없으면 `SKILL.md`를 먼저 채운다.
- **후속 연구 방향**: (i) 과업 수준 벤치마크(산출물 술어 기반 채점), (ii) 미리보기 충실도의 정량 지표, (iii) 백엔드 없는 환경에서의 검증 대체 경로, (iv) 리프팅 비용 대 절감 편익의 경제성 모델, (v) 여러 하네스가 공유할 계약의 최소 공통 부분집합.
