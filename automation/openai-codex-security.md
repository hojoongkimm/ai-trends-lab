## 1. 연구 배경 및 시스템 병목 (Systems Research Problem)

정적 분석(SAST)과 LLM 기반 코드 감사의 실패 원인은 "결함을 못 찾는 것"보다 **찾은 것의 신뢰성과 회계(receipt)에 있다.** 운영 환경에서 관측되는 병목은 다음 네 가지다.

1. **거짓 경보의 경제학**: SAST 도구는 규칙 위반을 대량 보고하고, 그중 도달 가능성(reachability)이나 권한 상승 효과가 없는 항목이 다수를 차지한다. 트리아지 비용이 탐지 이득을 초과하는 순간 도구는 무시된다.
2. **환각된 취약점**: LLM 단독 감사는 "그럴듯한 공격 경로"를 서술하지만, 실제 강제 지점(enforcement point)이나 호출자 검증 없이 결론을 내린다. 반대로 "런타임 재현이 없다"는 이유로 심각도를 임의로 낮추는 반대 방향의 오류도 빈번하다.
3. **반복 스캔에서의 중복 폭발**: 같은 결함이 패스마다, 워커마다 다른 제목·다른 라인으로 재보고되면 백로그가 사실상 관리 불가능해진다. 중복 제거는 부가 기능이 아니라 **스캔 시스템의 1차 요구사항**이다.
4. **감사 범위의 불투명성**: "무엇을 보지 않았는가"가 기록되지 않으면, 결과가 비어 있는 스캔과 실패한 스캔을 구분할 수 없다.

`codex-security`는 결함을 **스키마를 가진 봉인 아티팩트(sealed artifact)** 로 격상하고, 스캔을 재현·재개 가능한 세션으로 취급하며, 탐지(discovery)·유효성 검증(validation)·패치·재검증(verification)을 분리된 단계로 강제한다. 즉 문제를 "모델이 취약점을 잘 찾는가"가 아니라 **"조사 결과를 어떻게 신뢰 가능한 기록으로 만드는가"** 로 재정의한 시스템이다.

## 2. 아키텍처 및 수학적 정식화 (Architecture & Formulation)

### A. 스캔 대상과 모드의 분리

대상 선택은 세 축으로 분리된다: 저장소/경로(`--path`), 커밋된 변경(`--diff <base>`), 작업 트리(`--working-tree`). 모드는 두 단계다.

- **Standard**: 기본 단일 패스 감사. 조사 시간은 `--max-time`(분)으로 **권고적(advisory)** 으로만 주어진다.
- **Deep**: Standard 감사를 배치로 **반복**하고 결과를 병합하는 다중 패스 감사. `--workers`로 동시 스캔 수, `--subagents`로 스캔당 서브에이전트 수를 제어한다.

이 분리는 비용·시간 의미론을 정확히 나눈다는 점에서 중요하다. Standard의 시간 제한은 소프트 데드라인이고, Deep의 discovery 데드라인은 **강제(enforced)** 되며 기본값과 상한이 5,760분(96시간)이다. 데드라인 전에 소스 리뷰가 하나도 완료되지 않았다면, 그 사실이 리포트와 매니페스트에 제한 사항으로 기록된다. "결함 0건 완료"와 "감사 미완료"를 구분하는 것은 보안 도구의 신뢰성에서 가장 기본적인 요건이다.

### B. 코어 감사의 실행 순서 (단일 자기완결 감사)

`core-scan.md`가 정의하는 워크플로는 다음 순서를 고정한다.

1. 정확한 대상·범위·상속된 `SECURITY.md`·사용자 컨텍스트·지식베이스를 확정한다. 지식베이스 사실이 생성된 가정보다 우선한다.
2. **독립 기준 감사(baseline auditor)** 를 포크 턴(`fork_turns: "none"`)으로 실행한다. 부모의 가설과 다른 조사 결과를 배제해 앵커링(anchoring)을 차단하는 장치다.
3. 위협 모델(`threat-model.md`)을 읽어 아키텍처와 신뢰 경계를 지도화한다. 아키텍처 매핑만으로 감사 커버리지가 완료되었다고 주장하지 않는다.
4. 공격자·보호 자산·진입점·기대 통제·민감 연산·소스 앵커별로 조사 패킷을 묶는다.
5. 패킷 단위로 워커에 위임하되, 반환된 후보와 반증(counterevidence)을 **결합·검증 전에** `record_codex_security_scan_draft`로 체크포인트한다. 후보는 `candidateId`와 `reviewState.deferred`(사유 + 원본 페이로드)로 보존되어, 중단 후에도 재개 가능하다.
6. 후보별로 소스에 대조해 검증하고, `scope`/`threatModel`/`findings`/`reviewState`를 스키마에 맞춰 조립한다.

명시적 금지 조항이 아키텍처를 규정한다: 별도 단계 스킬 호출, 순위화 단계, 파일별 원장(ledger), 단계별 워커 풀, 영수증 파일을 추가하지 말 것. 즉 **하나의 자기완결 감사 안에서 탐지·검증·공격 경로 추론을 완결**하며, 파이프라인 분해 편향(단계 사이에서 근거가 소실되는 문제)을 피한다.

### C. Deep Scan: 반복·병합·중복 제거의 정식화

Deep Scan은 Standard 감사를 최대 `--workers`개 배치로 반복하고, 배치가 완료되는 순서대로 병합한다. 각 워커는 자기가 보고한 근거를 직접 검증하며, 워커 간에 조사 리드를 교환하고 특정 소스 위치 확인을 서로 요청할 수 있다.

병합은 **소스 위치, 인용된 코드, 취약점 설명**의 일치를 근거로 반복 발견을 결합한다. 각 그룹은 첫 번째 설명과 모든 보고 위치, 그리고 원본 관측(observation)을 유지한다. 이후 배치에는 보유 결함의 제목과 주 위치가 전달되어, 워커가 아직 조사되지 않은 도달 경로를 파고들 수 있게 한다.

중복 결함을 하나로 묶는다는 것은 결함 집합 위의 동치 관계를 추정하는 문제다. 결함 $f_i$의 통제 실패 지점을 $c(f_i)$, 영향 경로를 $\pi(f_i)$라 할 때, 이상적 병합 술어는 다음과 같다.

$$
M(f_i, f_j) = \mathbb{1}\left[c(f_i) = c(f_j) \wedge \text{remediation}(f_i) \simeq \text{remediation}(f_j)\right]
$$

실무에서는 $c(\cdot)$이 직접 관측되지 않으므로, 위치·코드 인용·설명이라는 간접 신호로 근사한다. 이 근사의 두 오류 방향은 비대칭적 비용을 갖는다.

- **과병합(over-merge)**: 서로 다른 결함이 하나로 합쳐져 **결함이 조용히 사라진다**. 리포트에서 검증 가능한 최악의 실패다.
- **과소병합(under-merge)**: 중복이 남아 트리아지 부하가 증가하지만, 결함 자체는 보존된다.

따라서 병합 규칙은 재현율 쪽으로 보수적이어야 하며, 코드가 그룹화를 "동일한 깨진 통제와 동일한 실질적 교정"으로 한정하고 "공유된 CWE만으로는 병합 사유가 되지 않는다"고 명시하는 이유가 여기에 있다. 각 그룹이 **모든 위치를 보존**하는 것도 과병합 시 정보 소실을 줄이기 위한 장치다.

### D. 종료 규칙의 비용 구조

Deep Scan의 종료는 두 상한(총 시작 수 `--max-discovery-runs`, 시간)과 하나의 수렴 조건(`--stop-after-no-new`: 새 결함을 추가하지 않은 연속 완료 스캔 수)으로 결정된다. 패스당 "신규 결함 없음" 확률을 $q$라 두면, 상수 수확 체감 가정에서 종료까지의 기대 패스 수는 기하 분포의 연속 실패 대기시간으로 근사된다.

$$
\mathbb{E}[N] = \frac{1 - q^{s}}{(1 - q) q^{s}}, \qquad s = \texttt{stop-after-no-new}
$$

현실에서는 패스가 진행될수록 신규 결함률이 낮아지므로 $q$는 증가하고, 따라서 실제 기대 패스 수는 위 근사보다 **크다**. 이 비대칭이 바로 "수렴 조건만 두고 상한을 두지 않으면 비용이 통제 불가능해지는" 이유이며, 세 상한을 함께 두는 설계의 근거다. 시간 상한은 discovery만 중단시키고, 완료된 스캔의 결함은 반환한다 — 부분 결과의 보존이 전체 실패보다 우선한다.

### E. 결함의 정체성: identity, fingerprint, occurrence

스키마(`findings.schema.json`)의 필수 필드는 결함을 "이번 스캔의 관측"과 "저장소에 존재하는 결함"으로 분리한다.

| 필드 | 역할 |
| :--- | :--- |
| `findingId` / `occurrenceId` | 논리적 결함 식별자 / 특정 스캔에서의 발생 식별자 |
| `identity.anchor` / `identity.instance` | 통제(control) 수준 앵커 / 인스턴스 구분자 (소문자 슬러그 패턴 강제) |
| `fingerprints` | 재스캔·다른 워크트리에서의 재식별용 지문 |
| `severity` | `level`(critical~informational), `score`, `scoringSystem`, `vector`, `rationale`, `changeConditions` |
| `confidence` | `level`(high/medium/low) + `rationale` — **심각도와 분리** |
| `locations[]` | `path`, `startLine`, `endLine`, `role` |
| `provenance.source` | 실제 출처 |

`identity`가 통제 수준 앵커와 인스턴스를 분리하는 구조는 중복 제거와 재식별을 같은 좌표계에서 처리하게 해준다. 심각도에 `changeConditions`("이 조건이 바뀌면 등급이 달라진다")를 강제하는 것도 주목할 만하다. 이는 심각도를 정적 라벨이 아니라 **가정에 조건부인 판정**으로 만든다.

심각도 등급은 세 조건의 논리곱으로 정의된다: 접근성(누가 도달 가능한가) ∧ 영향(어떤 경계를 넘고 무엇을 얻는가) ∧ 근거(공격 경로가 소스로 입증되는가). Critical은 세 조건 모두, High는 하위 신뢰 행위자에 대해 세 조건, Medium 이하는 검증된 제약이 있을 때 부여된다. 반대로 "익스플로잇이 증명되지 않았다"는 사실만으로 등급을 낮추는 것은 금지되며, 누락된 사실은 **신뢰도(confidence)에 기록**된다. 이 분리 덕분에 심각도 분포는 보수적으로 유지되면서도, 미입증 항목이 조용히 사라지지 않는다.

### F. 검증·패치·재검증 루프

- `cs validate`: 결함을 설정된 모델 제공자에 보내 소스 근거로 평가한다. 리뷰 도구는 체크아웃을 읽을 수 있지만 **네트워크와 웹 검색은 비활성**이며, 빌드·테스트·PoC·애플리케이션 실행은 수행하지 않는다. 런타임 증명이 필요하면 별도 재현 단계를 분리하라는 것이 문서의 입장이다.
- `cs patch`: 저장 결함 또는 occurrence ID로 원본 저장소를 선택해 패치를 생성한다. `--assess-patch-risk`, `--create-pr`로 위험 평가와 초안 PR 생성까지 이어진다. 패치 위험 평가는 별도 스키마(`patch-risk-assessment.schema.json`)를 갖는다.
- `cs verify-fix`: 읽기 전용 샌드박스에서 수정 여부를 검사하고 `fixed`/`still_vulnerable`/`inconclusive` 판정과 근거를 반환한다. 종료 코드는 전부 수정 0, 잔존 취약 1, 판정 불가/실패 2다.

이 3단 루프의 의미는 "탐지 모델"과 "검증 모델"을 분리해 **자기 확신의 순환(self-confirmation)** 을 끊는 데 있다. 탐지 단계의 후보는 검증 단계에서 반증될 수 있고, 패치 단계는 다시 검증 단계에서 되돌려질 수 있다.

### G. 결정론적 실행 계층: 특권·경로·출력

자동화 도구로서의 안전 속성은 프롬프트가 아니라 실행 계층에 있다.

- `--output-dir`은 **비어 있고, 스캔 대상 및 상위 git 워크트리 밖**이어야 하며, 다른 사용자가 출력 디렉터리나 상위 경로를 교체할 수 없어야 한다(Windows는 소유자 검사까지 수행).
- 커밋 diff 스캔은 요청 헤드 리비전의 **깨끗한 전체 체크아웃**을 요구하고, `assume-unchanged` 플래그까지 검사한다. 로컬 변경이 있으면 스캔 전에 거부한다.
- SARIF는 `<scan-dir>/exports/results.sarif`로 자동 기록되며, 선택적 내보내기 실패가 스캔 완료를 막지 않는다. `--fail-on-severity`는 정책 위반에만 종료 코드 1을 부여하고, 무결성·필수 출력 실패는 2로 분리한다.
- 모든 아티팩트(리포트, 매니페스트, 초안, 커버리지)는 스키마 검증을 통과해야 완료된다. 레거시 별칭이나 형식이 어긋난 선택 필드는 **완료 전에 거부**되며 조용히 복구되지 않는다.

### H. 통합면과 확장

20개의 플러그인 스킬이 워크플로를 캡슐화한다(`security-scan`, `deep-security-scan`, `security-diff-scan`, `finding-discovery`, `validation`, `fix-finding`, `verify-fix`, `assess-patch-risk`, `attack-path-analysis`, `threat-model`, `threat-model-visualize`, `define-security-policy`, `publish-findings`, `track-findings`, `cloud-findings`, `resolve-dependency-alert`, `triage-finding`, `vulnerability-writeup`, `check-skills`, `propose-security-hardening`). 외부 도구와의 접점은 양방향이다: 유입은 Trivy, Endor Labs, Snyk, Wiz, SonarQube Cloud, GHSA, AWS Continuum, 그리고 제3자 스캐너 리포트 임포트, 유출은 SARIF/JSON/CSV, ServiceNow AVR, Linear/Jira/GitHub 이슈.

평가 체계도 저장소에 포함되어 있다(`evals/`): 합성 자격증명 탐지(`secret-discovery`), 시간 예산 유무의 **짝지은 비교**(`standard-time-budget`), 자연어 요청의 워크플로 라우팅(`workflow-routing`), 트리아지 판정의 OSS 캘리브레이션과 SastBench(`triage-finding`), 스킬 사전 설치 심사(`check-skills`). 상당수가 모델 호출 없이 결정론적으로 채점되는 하네스 검사를 갖는다.

| 도달 가능성 판단 | 제한적(설정 의존) | 서술적, 미입증 가능 | 강제 지점·호출자·차단 근거 확인 |
| 결과 형식 | 고정 리포트 | 자유 서술 | 스키마 봉인(identity·fingerprint·severity·confidence) |
| 반복 스캔 | 라인 기반 중복 | 중복 폭발 | 3신호 병합 + 보존적 병합 술어 |
| 범위 회계 | 파일 목록 | 대체로 없음 | `coverage.deferred` / `openQuestions` 분리 |
| 수정까지의 연결 | 별도 프로세스 | 부분적 | validate → patch → verify-fix 3단 루프 |
| 감사 재현성 | 도구 버전 의존 | 없음 | 매니페스트·세션 재개·24시간 후 재진입 정리 |

비용·시간 통제는 모드별로 다른 의미론을 갖는다는 점이 실무적으로 중요하다. Standard는 권고 예산으로 탐색 폭을 조절하고, Deep은 강제 데드라인과 수렴 조건으로 비용을 상한 처리한다. 두 모드를 같은 스캔 이력에 기록하면서도 설정을 혼합하지 않는 것(레시피에 해석된 deep 설정을 저장해 재개·재실행이 이후 기본값 변경에 영향받지 않게 하는 것)은 장기 운영에서 필수적인 설계다.

## 4. 한계점 및 실패 모드 (Limitations & Trade-offs)

1. **런타임 증명의 구조적 부재**: 검증은 소스 근거 기반이며 빌드·테스트·PoC·실행을 하지 않는다. 따라서 "소스상 도달 가능"과 "실제 익스플로잇 가능"의 간극이 남고, 설정·배포·게이트웨이 수준의 완화책은 모델의 추정에 의존한다. 문서가 이를 proof gap으로 명시하는 것은 정직하지만, 그 간극 자체가 오탐·과소평가의 원천이다.
2. **과병합의 비가시성**: 병합은 위치·코드 인용·설명의 유사도에 기반하므로, 하나의 통제 실패가 여러 곳에서 서로 다른 공격 경로를 만들 때 이를 하나로 접는 것이 옳은지 판단이 어렵다. 그룹이 모든 위치를 보존하지만, 서로 다른 교정이 필요한 두 결함이 병합되면 리포트의 실행 가능성은 떨어진다.
3. **깊이-비용의 볼록성**: Deep Scan의 수확은 패스 수에 대해 체감하지만 비용은 선형 이상으로 증가한다(워커·서브에이전트 병렬화는 처리량을 늘릴 뿐 총 토큰을 줄이지 않는다). 종료 규칙 파라미터($s$, 최대 실행 수, 시간)의 최적값은 저장소 규모·언어·결함 밀도에 따라 달라지며, 기본값이 모든 대상에 적합하다는 근거는 공개되어 있지 않다.
4. **모델·제공자 종속**: 기본 모델·effort가 특정 스냅샷(`gpt-5.6-sol`, `xhigh`)에 고정되어 있고, 모델 ID와 effort는 제공자에 그대로 전달된다. 모델 교체 시 결과 분포가 달라지며, 저장된 스캔의 재현은 원 버전에 의존한다. 일부 사이버 보안 요청과 보호된 결함은 접근 프로그램(Trusted Access/Daybreak) 승인을 요구하므로, 계정 등급이 결과 가용성에 영향을 준다.
5. **규모의 운영 비용**: 다중 저장소·컴포넌트 스캔, 대량 캠페인, 컨테이너 실행은 지원되지만 각 스캔이 독립 세션이므로 토큰·시간 비용이 선형 누적된다. 비용 상한(`maxCostUsd`)은 진행 중 요청이 상한을 초과할 수 있음을 스스로 명시한다.
6. **스키마 경직성**: 신규 초안은 최신 스키마를 강제하고 레거시 필드를 거부한다. 이는 데이터 품질에는 유리하지만, 미완료 초안은 원 버전으로만 완료할 수 있어 장기 보관 아티팩트의 유지보수 부담이 생긴다.
7. **탐지 편향의 불투명성**: 어떤 취약점 클래스(예: 비즈니스 로직 결함, 인가 모델 오류)에 강하고 어떤 클래스에 약한지에 대한 정량 벤치마크가 저장소에 공개되어 있지 않다. 평가 스위트는 자격증명 탐지·시간 예산·라우팅처럼 하네스 속성을 측정하는 데 집중되어 있어, **탐지 성능 자체의 외부 비교 수치**는 부재하다.

## 5. 연구 및 실무 활용 포인트 (Research Impact)

- **에이전트 보안 감사의 평가 방법론**: "결함을 몇 개 찾았나"가 아니라 ① 보고된 결함의 소스 근거 충족률, ② 병합 후 잔존 중복률, ③ 커버리지 회계의 정확성(미검토 영역이 기록되었는가), ④ 수정 검증 통과율로 평가 축을 분해하는 것이 재현 가능한 비교의 전제다. 이 저장소의 아티팩트 스키마는 그 측정 항목을 그대로 데이터 구조로 만든 사례다.
- **심각도와 신뢰도의 분리**: `severity`와 `confidence`를 별도 객체로 두고, 심각도에 `changeConditions`(등급을 바꿀 조건)를 붙이는 설계는 보안 리포트를 **조건부 판정들의 집합**으로 만든다. 이는 리스크 기반 우선순위화와 자동 게이트(`--fail-on-severity`)를 신뢰도 가중과 독립적으로 운용하게 해준다.
- **다중 패스 아키텍처의 일반화**: "반복 실행 + 근거 기반 병합 + 수렴 조건 + 강제 상한"은 취약점 탐지에 국한되지 않는다. 대규모 코드 감사, 규정 준수 검사, 데이터 품질 프로파일링처럼 **재현율이 중요하지만 비용이 비선형으로 증가하는** 모든 배치형 에이전트 작업에 동일한 골격을 적용할 수 있다.
- **후속 연구 방향**: (i) 병합 술어의 캘리브레이션 — 과병합/과소병합 비용을 명시적 손실함수로 두고 임계값을 학습하는 문제, (ii) 소스 근거와 런타임 증명을 결합한 하이브리드 검증(정적 후보 → 최소 재현 스크립트 자동 생성), (iii) 커버리지 회계를 이용한 신뢰구간 추정 — "미검토 영역의 결함 밀도"를 가정해 보고되지 않은 결함 수의 구간을 제시하는 통계적 접근, (iv) 모델 스냅샷 교체에 대한 결과 안정성(robustness) 측정.
